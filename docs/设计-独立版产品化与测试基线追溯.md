# 独立版产品化 + 测试基线可追溯 · 详细设计

> 版本：v1（设计稿） · 日期：2026-10 · 状态：待评审  
> 范围：**只做设计，不改代码**。覆盖两条工作流：
>
> - **A. 独立版产品化**：P0 打包 → P1 去 DSH 化 → P2 前后端分离部署
> - **B. 测试基线可追溯**：P0 基线 + 执行快照 → P1 场景资源 → P2 分析报告
>
> 结论先行：**同意“先 B1 基线 + 执行快照，再 B2 资源、B3 报告”的顺序**。  
> PR、需求、用例版本、场景资源、实际结果，只有挂在同一个“测试基线 + 测试运行”上才有对齐意义；否则只是各自多了一张表。

---

## 1. 目标与非目标

### 1.1 目标

1. **独立运行**：不安装 DSH，也能以 `autotest-server` 起一个完整前后端；支持纯 Web、Docker、桌面端。
2. **可选保留 DSH**：DSH 插件形态继续可用，作为“适配器/入口”而不是主依赖。
3. **可追溯**：任意一次执行都能回答：
   - 对应哪条需求（Requirement）
   - 对应哪个 PR / 合入提交
   - 用的是哪个仓库基线（commit / version）
   - 用的是哪条用例的哪个版本
   - 用了哪些场景资源和测试数据
   - 预期与实际分别是什么
4. **可复现**：同一个基线 + 同一组用例版本 + 同一组资源，可以重新跑；最新代码与当时测试代码并存、可对比，不直接 `git checkout` 共享 clone。
5. **可登记场景扩展**：找不到 demo 页面时，能把 OneBox 链接、本地 `.ets` 页面、测试资源、配置指导登记为一等资产，并被用例和报告引用。
6. **可产出报告**：从一次执行生成包含“输入快照 + 分析过程 + 结论”的 Markdown 文件，结论明确区分：用例预置 / demo / 库 / 环境 / 不确定。
7. **向后兼容**：现有 API、DSH 插件、旧数据、旧页面尽量不破坏；新能力用增量字段 + 特性开关。

### 1.2 非目标

- 不重写现有用例生成、遍历、Hypium 执行、覆盖矩阵、知识库。
- 不替代 GitCode / GitHub / Gitee 的 PR 系统；只做同步与关联。
- 不自动判断“库一定有 bug”；只做证据约束下的归因假设与人工验收。
- 不把历史执行“猜”出基线/版本；无法确认的一律标 `unknown`。
- 不在本期做多租户、计费、完整 CI/CD 平台。

### 1.3 设计原则

| 原则 | 落地 |
|---|---|
| 基线不可变 | `repo_snapshots` 一旦 ready 只读；构建/改 demo 在 run workspace 副本 |
| 每次运行有快照 | `test_runs` + `test_run_items` + `executions.case_snapshot_json` |
| 不伪造历史 | 旧执行 `baseline_id/case_version` 允许为 NULL，UI 显示“未知（历史数据）” |
| 增量迁移 | 新表 `CREATE IF NOT EXISTS`，新列 `ALTER`；旧二进制可回滚 |
| 同源优先 | 默认同源部署；分离部署通过 runtime config + CORS 白名单 |
| 双入口不互斥 | DSH 插件 / 独立服务器共用核心；DSH 代码只在适配层 |
| 证据优先 | 报告、归因、场景资源都保留可回查证据；无证据不给高置信度 |
| 资源可回退 | 场景资源/补丁只作用于 run workspace，原基线与仓库只读 |

## 2. 现状与差距（摘要）

| 能力 | 现状 | 本设计要补 |
|---|---|---|
| 独立运行 | `lib/standalone.js` + `dist/web` 已可跑，已做冒烟 | 打包成可安装的独立产品 |
| DSH 解耦 | `architecture-policy.yaml` 已把 DSH import 限制在白名单 | 去掉独立版 UI/默认值/文案中的 DSH 语义 |
| 前后端分离 | 默认同源；API/WS 地址写死同源；跨源默认拒绝 | runtime config + CORS/WS 白名单 + 反代方案 |
| 库版本 | `libraries.current_version/last_commit` 只保留最新 | 物理快照 + 每库逻辑基线 |
| 执行记录 | 只有 `case_id`，无基线/用例版本/结构化实际结果 | `test_runs` + execution 快照 + `actual_json` |
| 需求 | 只有 `cases.source` 文本 | `requirements` + 用例/PR 关联 |
| PR | 只有 `analyses` 分析 JSON | `pull_requests` 实体 + 合并提交 + 基线 + 测试状态 |

| 报告 | R5 输出 JSON 到工单；xlsx 导出 | `analysis_reports` + Markdown 文件 + 下载 |

> 复用原则：`cases/case_versions`、`testability` A/B/C/D、`test_resources`、`issue_tickets`、`knowledge`、`PR 分析` 都保留，做扩展而不是替换。

### 3.2 发布形态

| 形态 | 包/入口 | 依赖 DSH | 用途 |
|---|---|---|---|
| DSH 插件 | `dsh-autotest` + `lib/index.js` | 是 | 已有 DSH 用户的嵌入入口 |
| 独立服务器 | `autotest-server` + `bin/autotest-server.js` | 否 | 纯 Web / Docker / 内网服务器 |
| 桌面端 | `autotest-desktop`（Tauri） | 否 | Windows 单机 |
| 前端静态包 | `autotest-web`（`dist/web`） | 否 | Nginx/CDN 分离部署 |

**推荐**：代码仍保留单仓双入口；**发布物拆成两个包**：

- `dsh-autotest`：DSH 插件包（`main` 指 `lib/index.js`，保留 client/Dsh 依赖）。
- `autotest-server`：独立包（`main/bin` 指 `lib/standalone.js`，只含 `lib` + `dist` + `skills`，无 DSH peer）。

这样不需要重构源码目录，又能让独立用户安装到不带 DSH 名称/依赖的包。

## 4. 工作流、优先级与依赖

| ID | 工作流 | 内容 | 依赖 | 建议顺序 |
|---|---|---|---|---|
| **B1** | 基线 + 执行快照 | `repo_snapshots`、`test_baselines`、`test_runs`、`executions` 快照、计划选择基线、执行详情 | 无 | **第 1** |
| **A1** | 独立版打包 | `autotest-server` 包、`bin`、`files`、CI 产物、Docker | 可与 B1 并行 | 第 1–2 |
| **A2** | 去 DSH 化 | edition、UI 文案、默认数据目录、模型配置、`/models/dsh-default` 收口 | A1 | 第 2 |
| **B2** | 场景资源 | `scenario_assets` + 本地文件/OneBox/配置指导 + 用例关联 + run 应用 | B1 | 第 3 |
| **A3** | 分离部署 | runtime config、API/WS base、CORS 白名单、Nginx/Docker 方案 | A2 | 第 3 |
| **B3** | 分析报告 | 报告上下文、归因枚举、Markdown 文件/下载、验收沉淀 | B1 + B2 | 第 4 |
| **B4** | 需求/PR 追踪 | requirements / pull_requests / 关联 / UI | B1（可先只落库） | 与 B2/B3 并行 |

> 关键路径：**B1 → B2 → B3**。  
> A1/A2/A3 是独立产品化线，不阻塞 B1；但 A2 的“独立版配置”会和 B1 的“数据目录/基线目录”共用配置项，需要同一份设计。

## 6. 基线与执行快照设计（B1）

### 6.1 为什么是“物理快照 + 逻辑基线”两层

单体仓里 171/269 个库共用一个仓库。如果每个库都单独 clone 一份，磁盘会爆；如果只有一个共享 clone 并直接 `git checkout`，又无法“最新与当时版本并存”。

因此：

- **物理层** `repo_snapshots`：每个仓库每个 commit 一份只读检出（worktree 或只读目录）。
- **逻辑层** `test_baselines`：每个库引用一个物理快照 + `repo_subpath`，形成“这个库的 B-xxx 基线”。
- 同一 commit 下 10 个库 = 1 份物理目录 + 10 条逻辑基线。

### 6.2 创建基线

入口：

- 从 PR：`POST /libraries/:id/baselines {source:'pr', prId}`；
- 从 commit/tag：`{source:'tag'|'manual', ref:'v1.2.0'|'abc1234'}`；
- 从当前最新：`{source:'latest'}`；
- 运行时懒创建：计划 `baseline_mode=latest` 且无 ready 基线时。

流程：

1. 规范化 `repo_url`；检查库存在。
2. 解析 commit：
   - PR：优先 `merge_commit_sha`；没有则用 `head_sha`，并标注 `mergeCommitMissing=true`；
   - tag/commit：`git rev-parse` 校验；
   - latest：当前 `repositories` 工作 clone 的 HEAD / `libraries.last_commit`。
3. `repo_snapshots` 插入 `creating`；入任务 lane（复用现有 task/lane）。
4. `git fetch`；确认 commit 存在。
5. 创建只读检出：
   - 优先 `git worktree add --detach <workspace>/baselines/<repo>/<commit> <commit>`；
   - worktree 不可用 / 路径过长时，退化为 `git archive` 或只读复制；
   - 写 `.autotest-baseline.json`：`{repoUrl, commit, versionLabel, source, prId, createdAt}`。
6. 校验 `repo_subpath` 存在；解析 `bundleName/mainAbility`（只读）。
7. 计算 `size_bytes`；`repo_snapshots.status=ready`。
8. 为每个目标库插入 `test_baselines`（`ready`），关联 `baseline_prs`。
9. 若来源 PR，写 `baseline_prs(relation='source')`；批量合入可追加 `included`。

失败处理：`status=failed` + `error`；不留下半成品目录（或保留 `.failed` 供排查，但不进入可选列表）。

### 6.3 目录与清理

```
<workspace>/
  repos/<owner>_<repo>/                  # 最新工作 clone（可变）
  baselines/<repo>/<commit>/             # 只读物理快照
  runs/<runNo>/<lib>/                    # 运行副本（可构建）
  scenario-assets/<lib>/<assetNo>/       # 场景资产
  reports/<lib>/<reportNo>.md            # 分析报告
  demo-patches/<baseline>/<caseNo>/      # 补丁副本（扩展：按基线隔离）
```

清理策略：

- `baseline.retainDays`（默认 90）：未被执行/报告/工单引用的旧基线可清理；
- `baseline.maxTotalGb`（默认 50）：超限按最早未引用淘汰；
- 清理前必须检查引用；硬删需 admin + 审批；
- 报告/知识库默认长期保留。

### 6.4 一次运行发生什么

`POST /plans/:id/run` 或 `POST /libraries/:id/runs`：

1. **解析基线**：按 `plan.baseline_mode` 选择 `baseline_id`；不存在则懒创建。
2. **创建 `test_runs`**：`run_no`、`plan_id`、`trigger`、`status=pending`。
3. **为每个库创建 `test_run_items`**：
   - 选 `baseline_id`、`commit_sha`、`repo_subpath`；
   - 读取该库所有计划内用例的 `current_version`，写入 `case_versions_json`；
   - 分配 `workspace_rel_dir = runs/<runNo>/<lib>`；
   - 选资源集合 `resource_set_id`。
4. **创建运行副本**：从 baseline 复制到 `runs/...`（排除 `.git/build/node_modules` 等，复用 `makeCopy` 逻辑）；**不在 baseline 上构建**。
5. **应用场景资产/补丁**：把 `run_item_assets` 里的资产复制/注入到运行副本；写 `apply` manifest；失败则该运行失败并写明原因。
6. **环境准备**：`env_run_id`；在运行副本目录执行 `ohpm_install/build/...`。
7. **执行用例**：按 `case_versions_json` 读取 `case_versions.snapshot`，逐条执行；每次执行写：
   - `test_run_id`、`run_item_id`、`baseline_id`、`case_version`、`case_snapshot_json`、`library_version`、`commit_sha`；
   - `actual_json`（逐步骤/判据/证据）；
   - `steps/logs/thinking` 仍保留。
8. **终态**：`test_run_items` 汇总；`test_runs` done/failed；计划状态更新。
9. **报告入口**：失败执行可一键建工单/报告。

### 6.5 用例版本快照

- 运行开始读取 `cases.current_version` 与 `case_versions.snapshot`；
- 写入 `test_run_items.case_versions_json`；
- 每条执行写 `case_version` + `case_snapshot_json`；
- 运行中用例被编辑/回滚，不影响本次；下次运行取新版本。
- 若某用例在计划运行前被删除：该条标记 `skipped` 并写明“用例已删除”，不伪造快照。

### 6.6 实际结果 `actual_json`

必须至少覆盖：

- 每步：`seq/desc/status/expected/actual/durationMs/log/evidence`；
- 每个 oracle：`type/target/expected/actual/status/evidence`；
- 设备、环境、基线、用例版本；
- 产物（截图/日志/报告）路径 + sha256；
- 失败原因。

现有 `planExecutor` 只写一条“运行 Hypium 脚本”的步骤；B1 要求至少写：
- 若执行器只有整批脚本结果，则 `steps` 写一条 summary，但 `actual_json.result` 必填、`case_snapshot_json` 必填；
- 后续 `dryRun`/逐步骤执行再补全 `steps`（不阻塞 B1）。

### 6.7 历史数据

- 现有 `executions` 的 `baseline_id/case_version/commit_sha` 全部 NULL；
- UI 显示“未知（历史数据）”，不参与“可复现”筛选；
- 不根据 `libraries.last_commit` 反推旧执行版本；
- 新运行从 B1 上线后开始积累。

## 7. 需求、PR 与基线追踪（B4）

### 7.1 需求

- 需求可以来自 OneBox/需求单，也可以手工建；
- 只存 `external_id + url + acceptance_md`，不复制外部系统全文（避免同步冲突）；
- 用例通过 `requirement_cases` 多对多关联；
- PR 通过 `pr_requirements` 关联；
- 列表页显示：需求状态、关联用例数、关联 PR 数、最近失败执行数、覆盖基线数。

### 7.2 PR 同步

- provider 适配器：GitCode 优先；GitHub/Gitee 可后续；
- 必须保存：`state`、`base_branch`、`head_sha`、`merge_commit_sha`、`merged_at`；
- 拿不到 `merge_commit_sha` 时：
  - 允许建立“PR head 基线”，标注 `source='pr-head'`；
  - UI 显示“非合入提交，仅用于预验证”；
  - 不伪造成“已合入”。
- 本地 git 降级：只作为 `provider='local'` 的提交记录，不冒充 PR。

### 7.3 测试状态

PR 的测试状态不由 PR 表自己维护，而是**派生**：

- 该 PR 关联的 `baseline_id` 下，有哪些 `test_run_items` / `executions`；
- 统计：`untested / testing / passed / failed / partial`；
- 规则：
  - 无执行 → `untested`；
  - 有失败 → `failed`；
  - 全通过 → `passed`；
  - 混合/跳过 → `partial`。
- 这样避免“PR 上手动点一个状态”与真实执行不一致。

### 7.4 从 PR 建立基线

`POST /libraries/:id/baselines {source:'pr', prId}`：

1. 取 PR 的 `merge_commit_sha`；
2. 创建 `repo_snapshot`（`source='pr'`, `source_pr_id`）；
3. 创建 `test_baseline`；
4. 关联 `baseline_prs`；
5. UI 跳转“选择用例跑一次”。

## 8. 场景资源与测试资源（B2）

### 8.1 为什么单独建 `scenario_assets` 而不是继续扩 `test_resources`

现有 `test_resources` 是“数据类资源”（animation json / fixture / 证书 / 图片 / 媒体 / config），适合放“输入数据”。

但用户说的是“找不到某个 demo 页面”“本地单个 `.ets` 页面”“OneBox 链接”“配置指导”。这些是**测试场景资产**，不仅是数据：

- 有页面/入口；
- 有配置步骤；
- 有适用版本；
- 可能由多个文件/资源组成；
- 需要版本、校验、复用、关联用例。

因此：

- `test_resources` 保留为数据资源；
- `scenario_assets` 作为场景资产主表；
- 通过 `test_resource_set_items` / `scenario_asset_files` 关联。

### 8.2 三类来源

| kind | 说明 | 存储 |
|---|---|---|
| `onebox_link` | OneBox 文档/页面链接 | 只存 `uri` + `config_guide_md`，不抓取内容 |
| `demo_page` | 本地 `.ets` 页面/入口/路由改动 | 存 `rel_dir` + `scenario_asset_files` + manifest |
| `fixture` | 数据文件/资源 | 可引用 `test_resources`，也可存本地 |
| `config` | 环境/配置指导 | `config_guide_md` + 可选配置文件 |
| `mixed` | 以上组合 | 文件 + 链接 + 指导 |

### 8.3 本地资产目录

```
<workspace>/scenario-assets/<lib>/<assetNo>/
  manifest.json          # 文件清单、入口、适用版本
  README.md              # 配置指导（从 config_guide_md 生成）
  pages/Entry.ets        # 示例
  resources/sample.json
```

`manifest.json` 至少包含：

```json
{
  "assetNo": "SA-...",
  "library": "...",
  "kind": "demo_page",
  "scenarioKind": "boundary",
  "entryHint": "pages/Index.ets 增加入口按钮",
  "files": [{ "path": "pages/Entry.ets", "sha256": "..." }],
  "compat": { "minVersion": "v1.2.0", "maxVersion": "", "commit": "" }
}
```

### 8.4 应用方式

- **不修改 baseline**；
- 在 `runs/<runNo>/<lib>` 运行副本上应用：
  - `copy` 文件到目标路径；
  - 若需要改 `main_pages.json` / 首页入口，按 `apply.json` 的补丁执行；
  - 写 `run_item_assets.apply_status` + `manifest_json`；
  - 失败则该资源标记 `failed`，运行可继续但报告必须写明“资源未应用”。
- 对 `onebox_link`：不复制内容；运行前检查链接可访问（可选），报告记录链接与访问时间。
- 对 `fixture`：复制到运行副本的资源目录，并在用例步骤/脚本中注入路径。

### 8.5 校验

分三级，按需执行：

1. **静态**：路径安全、sha256、manifest 完整、文件大小限制；
2. **编译**：在临时副本执行 `devecocli build`（走现有 envkit/脚本资产），记录产物；
3. **真机**：运行入口页面，抓 UI dump/截图，确认能到达。

`validation_json` 存证据；`status=validated` 只能由静态 + 编译（或人工确认）达成。

### 8.6 关联用例与需求

- `scenario_asset_cases(asset_id, case_id, role='precondition')`；
- 用例详情“前置资源”区展示；
- 用例 `precondition` 文本可保留，但结构化引用以 asset id 为准；
- 报告上下文读取关联资产（链接、配置指导、文件清单）。

### 8.7 资源集合

一次运行可包含：

- 场景资产（页面/链接/配置）；
- 数据资源（`test_resources`）；
- 设备/环境。

`test_resource_sets` 记录版本与 sha；`executions.resource_set_id` 指过去。这样“这次失败是不是因为资源换了版本”可查。

## 9. 分析与 Markdown 报告（B3）

### 9.1 触发方式

推荐从**执行**发起，而不是只从用例：

- 执行详情 → “以此执行建工单”；
- 工单自动带 `execution_id / test_run_id / baseline_id / case_version`；
- 也保留从用例发起（`execution_id` 为空，使用最近执行，但必须标注“未绑定具体执行”）。

### 9.2 上下文（在现有 R5 上补）

现有 R5 已有：目标页源码、真机遍历 dump、相关符号、最近执行日志、步骤、预期、oracle、README。

B3 新增：

| 输入 | 来源 |
|---|---|
| 预置条件 | `cases.precondition` + `case_snapshot_json.precondition` |
| 基线/commit | `test_baselines` / `repo_snapshots` |
| PR diff | `pull_requests.files_json` + 可选 git diff |
| 结构化实际结果 | `executions.actual_json` |
| 场景资产 | `scenario_asset_*` + `config_guide_md` |
| 环境 | `env_runs` / `env_run_steps` |
| 资源版本 | `test_resource_sets` / `run_item_assets` |
| 执行/设备 | `executions` / `devices` |

**关键纪律**：分析代码必须来自该执行的 baseline/run workspace，而不是“当前最新 clone”。

### 9.3 归因结论

`RootCauseVerdict` 增加：

```json
{
  "attribution": "case_precondition | demo | library | environment | flaky | unknown",
  "rootCause": "...",
  "confidence": 0,
  "evidence": [
    { "kind": "source|symbol|explore|execution|readme|asset|pr", "ref": "...", "line": 0, "excerpt": "...", "supports": "..." }
  ],
  "fixSuggestions": ["..."],
  "needsDemoPatch": false,
  "uncertainties": ["..."],
  "analysisBy": "llm"
}
```

`needsDemoPatch` 保留兼容，但不再作为唯一“demo 问题”标志；`attribution` 是主结论。

### 9.4 分析过程

报告必须能写出“怎么排除的”，至少记录：

- 假设列表；
- 每条假设检查了什么（源码/日志/遍历/资源）；
- 结果（成立/排除/不确定）；
- 证据引用。

实现上可把 `analysis_steps_json` 存到 `issue_tickets.input_snapshot_json` 或 `root_cause_json` 的 `process` 字段；报告按模板渲染。

## 10. API 设计

### 10.1 约定

- 前缀：`/api/autotest`（不变）。

## 12. 独立版打包与去 DSH 化（A1/A2）

### 12.1 打包方案（推荐：同一份构建，两个发布包）

不重排源码，只做发布物分离：

- `dsh-autotest`：现有 DSH 插件包；
- `autotest-server`：独立包，由 `build:standalone` 产物 + 独立 `package.json` 生成。

`autotest-server` 的 `package.json` 建议：

```jsonc
{
  "name": "autotest-server",
  "version": "1.0.0-rc.1",
  "type": "module",
  "main": "lib/standalone.js",
  "bin": { "autotest-server": "bin/autotest-server.js" },
  "exports": {
    ".": "./lib/standalone.js",
    "./package.json": "./package.json"
  },
  "files": [
    "lib",
    "dist",
    "bin",
    "skills",
    "skills-lock.json",
    "README-standalone.md"
  ],
  "engines": { "node": ">=20" },
  "dependencies": {
    "better-sqlite3": "...",
    "ioredis": "...",
    "mysql2": "...",
    "node-cron": "...",
    "xlsx": "..."
  }
}
```

`bin/autotest-server.js`：

```js
#!/usr/bin/env node
import('../lib/standalone.js');
```

构建/发布：

1. `npm run build:standalone` → `lib/` + `dist/web`；
2. `npm run pack:standalone` → staging + `npm pack`；
3. CI 产出 `autotest-server-<version>.tgz` / zip / Docker 镜像；
4. 校验包内包含 `dist/web/index.html`、`lib/standalone.js`、`skills-lock.json`；
5. 干净目录安装，`npx autotest-server` 启动冒烟。

### 12.2 去 DSH 化

| 位置 | 现状 | 改法 |
|---|---|---|
| 包名/描述 | `dsh-autotest` | 独立包 `autotest-server`；DSH 包保留 |
| `main`/`bin` | 插件入口 | 独立包 `main/bin` 指 standalone |
| peerDependencies | DSH 两个包 | 独立包不声明；DSH 包保留 |
| 数据目录 | 源码下回退 `~/.dsh/autotest/data` | 独立版默认 `<installRoot>/autotest-data` 或 `AUTOTEST_DATA_DIR`；DSH 不变 |
| 工作区 | `cwd/workspace` | 独立版启动器默认 `<cwd>/workspace`，文档要求显式设置 |
| 模型 | 独立版已有 `models` | 去掉“复用 DSH 设置”文案；首次配置引导 |
| `/models/dsh-default` | 独立版也返回 DSH 默认 | 仅 `edition=dsh` 启用；独立版 404 或 `{dshDefault:null}` |
| health service 名 | `dsh-autotest` | `autotest-standalone` / `autotest-dsh` |
| 技能 | 依赖仓库 `skills/` | 独立包包含 `skills/` + lock；保留 `AUTOTEST_SKILLS_DIR` |
| 前端文案 | “DSH 风格/复用 DSH” | 独立版用中性文案；DSH 嵌入版保留 |
| client 插件 | DSH 专用 | 不随独立包分发；保留在 DSH 包 |

**edition 判定**：

- DSH 插件入口显式 `edition=dsh`；
- `bin/autotest-server` 设置 `AUTOTEST_EDITION=standalone`；
- 桌面端设置 `AUTOTEST_EDITION=desktop`；
- 前端读取 `/runtime-config` 或 `window.__AUTOTEST_CONFIG__.edition`。

**数据目录兼容**：

- DSH：保持 `<DSH profile>/autotest-data`；
- 独立版：`AUTOTEST_DATA_DIR` > `<installRoot>/autotest-data`；
- 源码 checkout 且无显式配置：`<cwd>/autotest-data`（不再默认 `~/.dsh`）；
- 首次启动检测旧 `~/.dsh/autotest/data`：只提示 + 提供 `npm run data:import-legacy`（复制并备份），**不静默切换**，避免空库。

### 12.3 验收

- `npm pack` 包含 `dist/web` / `skills`；
- 干净目录安装，无 `@deepseek-ai/*`，`npx autotest-server` 可启动；
- `/healthz`、`/api/autotest/health`、`/` 200；
- 独立版 UI 无 DSH 文案；
- 数据/工作区重启后保持；
- DSH 插件包仍可安装、功能不回退。

## 13. 前后端分离部署（A3）

### 13.1 三种拓扑

**A. 同源全栈（默认，推荐内网）**

```
浏览器 → https://autotest.example.com
          ├─ /           静态 dist/web
          └─ /api/autotest/* → Node :3280
```

**B. 同域反代（推荐生产）**

```
浏览器 → Nginx :443
          ├─ /            /srv/autotest/web
          ├─ /api/autotest/ → 127.0.0.1:3280
          └─ /api/autotest/ws → 127.0.0.1:3280 (Upgrade)
```

**C. 跨域分离（前端 CDN + API 独立域名）**

```
浏览器 → https://ui.example.com  静态
          └─ fetch/ws → https://api.example.com/api/autotest
```

### 13.2 runtime config

新增 `dist/web/config.js`（构建时默认，部署时可覆盖）：

```js
window.__AUTOTEST_CONFIG__ = {
  edition: "standalone",
  apiBase: "/api/autotest",
  wsBase: "",
  features: { baseline: true, scenarioAssets: true, mdReport: true }
};
```

前端解析顺序：

- `window.__AUTOTEST_CONFIG__.apiBase`；
- `import.meta.env.VITE_API_BASE`；
- 默认 `/api`（开发代理）。

`ws.ts`：

- `wsBase` 优先；
- 否则由 `apiBase` 推导协议+host；
- 路径固定 `/api/autotest/ws`；
- 跨域时 `wss://api.example.com/api/autotest/ws`。

### 13.3 CORS / WS 来源

新增环境变量：

| 变量 | 说明 |
|---|---|
| `AUTOTEST_CORS_ORIGINS` | 逗号分隔白名单，如 `https://ui.example.com` |
| `AUTOTEST_ALLOW_CROSS_ORIGIN` | 旧开关，保留兼容；新部署优先白名单 |
| `AUTOTEST_PUBLIC_API_BASE` | 可选，返回给 `/runtime-config` |
| `AUTOTEST_PUBLIC_WS_BASE` | 可选 |

行为：

- 无白名单：仅同源，保持现状；
- 有白名单：允许匹配的 `Origin`，返回 `Access-Control-Allow-Origin`、`Vary: Origin`、允许 `Authorization/Content-Type`、`OPTIONS` 204；
- 预检不要求认证；
- WS 握手检查 `Origin`，不在白名单则 403；
- 不使用 `*` + credentials；本项目用 `Authorization` 头，不依赖 Cookie。

### 13.4 反代示例（Nginx）

```nginx
server {
  listen 443 ssl;
  server_name autotest.example.com;

  root /srv/autotest/web;
  index index.html;

  location / {
    try_files $uri /index.html;
  }

  location /api/autotest/ {
    proxy_pass http://127.0.0.1:3280;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 600s;
  }

  location /api/autotest/ws {
    proxy_pass http://127.0.0.1:3280;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_read_timeout 3600s;
  }
}
```

### 13.5 Docker 方案（建议）

- `web`：Nginx，挂载 `dist/web` + `config.js`；
- `server`：`autotest-server`，挂载 data/workspace；
- `mysql`、`redis`；
- 同源反代；`server` 不暴露公网；
- healthcheck：`/healthz`；
- 数据卷：`autotest-data`、`autotest-workspace`、`baselines`、`reports`。

### 13.6 安全清单

- TLS/HSTS；仅内网可先 HTTP；
- 认证开启（API Key/RBAC）；不要匿名暴露 `0.0.0.0`；
- CORS 白名单最小化；
- WS token 不写日志；
- 上传限制大小/条目数/路径穿越；
- 报告/基线目录只读权限；
- 定期清理旧基线/运行副本；
- 反向代理限制请求体大小（现有 2MB；上传接口单独放宽）。

## 14. 迁移方案

### 14.1 Schema 迁移顺序

1. 新表 `CREATE TABLE IF NOT EXISTS`（SQLite + MySQL）。
2. 新列 `ALTER TABLE`（只加列，不改旧列）。
3. 新索引。
4. 新设置项（默认关闭/开启）。
5. 数据回填（只做可信的；否则 NULL/unknown）。
6. 启动自检：表/列存在、旧数据可读。

### 14.2 新表清单（迁移脚本同步）

### 14.4 回填规则

| 数据 | 处理 |
|---|---|
| 旧 `executions` | 新列 NULL / `'{}'`；UI 显示“未知（历史数据）”；不反推 |
| 旧 `issue_tickets` | `execution_id/baseline_id` NULL；`attribution='unknown'`；报告按需生成 |
| 旧 `analyses` kind=pr_analysis | 可选：解析 `content.prNumber/title/webUrl` 建 `pull_requests`，`provider='legacy'`、`state='unknown'`、`merge_commit_sha=''`；不做权威使用 |
| 旧 `cases` | 不建需求关联；不伪造 `case_version` |
| 旧 `test_resources` | 保留；可被 `test_resource_set_items` 引用 |
| 旧 `demo_patch_json` | 保留；不自动转场景资产（一次性补丁不是可复用页面） |
| 旧 `libraries.last_commit` | 不用于反推历史执行；可作为“最新基线”懒创建输入 |

### 14.5 SQLite → MySQL

- `migrate-sqlite-to-mysql.ts` 的表清单加入新表；
- 按现有方式保留 id、行数校验、可重复执行；
- 新表为空时也建表；
- 报告/基线目录不随 DB 迁移，需单独拷贝（文档说明）。

### 14.6 数据目录迁移（独立版）

- 不改变 DSH 的数据目录解析；
- 独立版新装：`AUTOTEST_DATA_DIR` 或 `<installRoot>/autotest-data`；
- 旧 DSH 数据：提供显式导入命令（复制 + 校验 + 备份），不静默；
- 工作区：独立版默认 `<cwd>/workspace`，支持配置；不自动搬旧 workspace；
- 启动日志打印实际 data/workspace/baseline 根目录。

### 14.7 回滚

- 全部为增量表/列；旧版本二进制可忽略新表/列；
- 新功能用 `feature.*` 开关关闭；
- 基线/报告文件独立存放，回滚不删除；
- 若必须回滚 schema，保留备份库，不在生产直接 `DROP`。

## 17. 风险与待确认

| 风险 | 影响 | 应对 |
|---|---|---|
| 单体仓基线磁盘 | 多个 commit 占用大 | worktree/只读快照 + 引用计数 + 配额；按仓库而非按库 |
| `devecocli build` 改工程 | 污染基线 | 只在 run workspace 副本构建；基线只读 |
| PR merge commit 缺失 | 无法精确复现 | 用 head 预验证并标注；合入后补 merge commit |
| 旧数据无版本 | 历史不可追溯 | 标 unknown；不伪造；新数据积累 |
| 跨域 CORS/WS | 部署失败/安全风险 | 默认同源；白名单；反代优先 |
| 场景资产上传 | 路径穿越/zip bomb | 大小/条目/路径/符号链接限制 |
| 报告 LLM 不可用 | 无结论 | 明确失败/未分析；不降级规则；保留上下文 |
| 多库计划 | 基线/资源组合复杂 | `test_run_items` 按库；先单库跑通 |
| 用例删除 | 历史快照丢失 | `executions.case_snapshot_json` 保存快照；用例删除建议软删 |
| 独立包与 DSH 包漂移 | 两套构建不一致 | 同源构建；CI 双包冒烟 |

**待确认**：

1. PR 主平台是 GitCode 还是 GitHub/Gitee？决定适配器优先级。
2. 是否接受“独立包 `autotest-server`”与 `dsh-autotest` 双包发布？
3. 场景资产是否允许上传任意 `.ets`，还是只允许“补丁 + 配置指导”？
4. 基线默认保留策略（天数/容量）。
5. 需求是否只存 OneBox 链接，还是需要同步需求点？
6. 是否要求前后端跨域分离，还是同域反代即可？
