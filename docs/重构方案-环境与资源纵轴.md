# AutoTest Agent 重构方案 —— 补上「环境与资源」纵轴

> 版本：v2（全量库规模化修订） · 日期：2026-10 · 状态：执行中（R0 已完成）
> 依据：`README.md`、`autotest/README.md`、`docs/架构评审-2026-09-21.md`、`docs/企业级对标评估-ZCode-2026-10-12.md`，以及对 `dsh-autotest/src`（25k 行）全量通读后的诊断。

---

## 0. 一页结论

**现状的结构性问题不是"功能不够"，而是"主轴错了"。**

现有 P1–P11 的工程量，约 90% 花在「用例 → 覆盖矩阵 → 脚本 → 执行 → 归因」这条**链尾**；
而「克隆 → 依赖 → 构建 → 装包 → 资源 → 环境」这条**链头**在代码里近乎为 0
（全库检索无任何 `ohpm install` / `hvigorw` / `hdc install` / har·hap 构建调用，
`hypiumRunner.ts` 只负责跑 Python 脚本，前提是"包已经装在机器上"）。

测试自动化平台的真实价值是：

> **让任意一个三方库在 30 分钟内进入"可自动测试"状态，并且每一次失败都让平台变得更聪明。**

前者靠 **环境画像 + 脚本资产库 + 预设库**，后者靠 **知识库沉淀**。两者缺位时，
前面生成得再漂亮的用例也只是"给了一份方案"——这正是"没切中要害"的根因。

**重构主张：不推倒重来，补纵轴。** 保留三入口、md 唯一事实源、规则注入、技能锁、
RBAC/审批/指标/WS、task lane、agent 接口层、demo 副本补丁机制、31 套离线自检纪律；
新增 6 个领域对象，把平台核心对象从"用例"改为"**一次可复现的测试运行**"：

```
一次运行 = 代码(commit) × 环境画像(profile) × 资源集(resources) × 用例 × 设备
```

## 0.5 全量库规模化策略（v2 新增，本方案的核心约束）

**目标是全量库（当前随包目录 348 个），不是拿 lottie 打个样。** lottie 只是动画类别的
样板库，用来验证链路；真正的交付是"348 个库都能被分层处理"。

### 0.5.1 为什么不能"每个库让 AI 跑一遍"

348 个库，即使每个库只做一次轻量 LLM 分析（约 8k tokens 输入 + 2k 输出），也是
**约 350 万 tokens 输入**；再叠加环境准备真机验证，时间与成本都不可控，且**同一类库的
分析结论高度重复**——动画类库的依赖形态、构建方式、资源构造几乎同构，逐库问 LLM 是把
同样的钱花 348 遍。

产品上的答案是：**AI 的单位成本从"每库"降到"每类 + 每异常"。**

### 0.5.2 四级分层（L0→L3）

```
全量库（348）
   │
   ├─ L0 静态画像（零 LLM，确定性）         ← 100% 覆盖，批量并发
   │     读：README / oh-package.json5 / build-profile.json5 / 工程结构
   │         / .gitmodules / *.so·*.a / 样本资源文件
   │     出：library_facts（类别、构建目标、依赖声明、二进制产物、
   │         资源候选、README 情报、可测性初判）
   │
   ├─ L1 预设匹配（零 LLM）                 ← 命中即得方案
   │     library_facts.kind → presets/<kind>/ → env_profiles(status=draft, source=preset)
   │
   ├─ L2 LLM 增量（仅差异库）               ← 只跑 L0/L1 搞不定的
   │     触发条件（任一）：
   │       · 类别未识别（kind = unknown）
   │       · README 含特殊前置条件（外部服务 / 特定 SDK 版本 / 硬件依赖）
   │       · 二进制依赖需要决策（预编译 vs 现编）
   │       · 该类别没有 preset
   │     出：env_profiles(source=ai_draft) + 不确定项 → 人工队列
   │
   └─ L3 人工确认                           ← 只处理真问题
         队列按「库类别 × 阻塞原因」聚合，一次解决一类，不是一次解决一个库
```

### 0.5.3 批量流水线（`library_survey`）

| 维度 | 设计 |
|---|---|
| 批次 | 一个批次 = N 个库的 L0→L1→(L2)，可指定库 / 按类别 / 全量 |
| 并发 | 受控并发（默认 4，可配），**不**一次性 348 个全开——git clone 与磁盘 IO 会打满 |
| 续跑 | 每库一行 `library_survey_runs`，状态幂等；重跑只补未完成/失败的 |
| 隔离 | 单库失败只记该库 error 与失败分类，不影响同批其他库 |
| 取消 | 复用 task lane 的 AbortSignal，批次可中途停 |
| 可观测 | 批次进度、每库状态、失败分类统计、L2 触发率 → 前端「全量分析」页 |
| 成本闸门 | L2 调用计入既有 `agent_events` token 记账与 `agent.maxTokensPerTask` 预算 |

### 0.5.4 全量推进路线（按类别分批，不是一次全跑）

1. **样板**：先跑通 1 个类别（animation，lottie 等）→ 验收 → 固化 preset；
2. **扩类**：按库数量从大到小推进类别，每批验收三项指标：
   - 画像完整率（L0 产出非空的库占比）
   - 预设命中率（L1 直接命中的库占比，目标 ≥ 70%）
   - 人工队列规模（L3 待处理条目，目标随类别增加而下降）
3. **收敛**：同一类库第二次跑时，L2 触发率应显著下降（知识库开始起作用）

### 0.5.5 由此带来的计划变化

| 原计划 | v2 调整 |
|---|---|
| R2 只做 lottie 资源样板 | R2 核心是**全量 L0 画像采集流水线** + 多类别 preset；资源样板降为类别内验证 |
| 用例生成按库逐个 LLM | 改为「L0 事实 → L1 预设 → L2 仅增量」，逐库 LLM 只在 L2 出现 |
| 人工队列按条 | 按「类别 × 阻塞原因」聚合，人一次解决一类 |
| 验收看单库演示 | 验收看**批次指标**（完整率/命中率/队列规模/L2 触发率） |

## 1. 问题诊断

### 1.1 问题一：`data/三方库测试表.xlsx` 没进库（三层脱节，非 bug）

| 层 | 现状（代码位置） | 后果 |
|---|---|---|
| 分发层 | `dsh-autotest/package.json` 的 `files: ["lib","cordis.patch.yml"]`；仓库根 `data/` 不在安装产物内；`desktop/scripts/stage-server.mjs` 只 `cp(lib)` / `cp(dist)` / `cp(skills)` | 新机器装完，插件数据目录里没有表 |
| 路径层 | `services/librarySheet.ts::resolveSheetPath()` 只找 `<数据目录>/三方库测试表.xlsx`，无"随包默认表"概念 | 表只能人工搬运 |
| 触发层 | `POST /libraries/sync-sheet` 是**手动 API**；启动只跑 `seed()`（仅注册 lottie 一个库） | 349 行目录对三个端均不可见 |

三个端数据目录是三套：`<安装根>/autotest-data`（DSH 插件）、`%APPDATA%\com.autotest.platform`（桌面端）、
`AUTOTEST_DATA_DIR`（独立版/CI）——但三者都走同一个 `db/sqlite.ts::dataDir()`，
所以"web 端和客户端都没有"是必然结果，而修复点也因此只需一处。

### 1.2 问题二：功能没切中要害

| 用户诉求 | 现状 | 缺口 |
|---|---|---|
| 测试环境（README 读取 + 每库预设方案） | 无 | 缺 `env_profiles` 领域对象、README 情报采集、预设库 |
| 二进制依赖 / 子模块 / 文件配置 | 无 | 缺环境画像的组件段与失败分类 |
| deveco-cli 成熟脚本库（克隆→装 hap→构建 har→XTS） | 无 | 缺脚本资产库（契约化）与统一 runner |
| 测试资源构造（lottie json、CA 证书、服务器库） | 无（`HypiumProjectTemplate/resource` 仅 2 个文件） | 缺 `test_resources`：模板 + 生成器 + 登记 + 复用 |
| 不只是给一份方案 | 当前确实只给方案 | 方案必须**可执行、可重试、可锁定、可归因、可复用** |
| AI + 用户反馈沉淀知识库 | 有框架（md wiki + 三级检索 + 无证据不许确认） | kind 仅 6 种且全在"遍历/判据"语义域，无环境/资源位置 |

## 3. 总体架构

### 3.1 新的执行链（5 段 → 8 段）

```
0. 目录引导    xlsx 导入 · 类别归类 · preset 匹配              ← R0
1. 环境画像    README + 仓库探测 + preset + 知识库召回          ← R2
2. 环境准备    clone → submodule → 二进制依赖 → ohpm
              → 构建 har → 构建 hap → hdc install → 冒烟      ← R1 / R4
3. 资源构造    模板实例化 → 校验 → 登记 → 复用                 ← R2
4. 用例生成    接口面 + 覆盖矩阵（现有能力，前移依赖 1/3）
5. demo 补丁   副本机制（现有，保留）
6. 脚本生成    Hypium 模板（现有，保留）
7. 执行        真机 + 判据真跑（现有）
8. 归因沉淀    失败分类 → 队列 → 知识条目（扩到 env/resource）  ← R3
```

每一段都挂现有 task lane / 事件流 / 审批闸门 / 取消信号，**不重写**。

### 3.2 新增领域对象

| 对象 | 表 | 解决问题 | 生产者 |
|---|---|---|---|
| 环境画像 | `env_profiles` | 这个库在什么工具链/SDK/依赖/配置下才测得动 | AI（README+探测+预设+知识库）出初稿 → 人确认 |
| 环境步骤与运行 | `env_profile_steps` / `env_runs` / `env_run_steps` | "从克隆到装包"每步可重试、有日志、有产物、有指纹 | 脚本库 runner |
| 脚本资产库 | `script_library` / `script_library_versions` | deveco-cli 脚本从散落 .sh 变成**带契约的资产** | 平台内置 + 人工扩展 |
| 测试资源 | `test_resources` / `test_resource_versions` | lottie json / CA 证书 / mock server / DB fixture 怎么构造、复用 | 模板 + 生成器 + 仓库检出登记 |
| 预设方案库 | `presets`（文件为事实源 + 索引表） | "每个库都已有预设方案"成为默认状态 | 按库类别维护 |
| README 情报 | `readme_intel` | README 里的依赖/构建命令/已知问题/样本资源位置 | AI 解析 → 不确定项进人工队列 |

### 3.3 目录结构（新增部分）

```
autotest/dsh-autotest/
  assets/三方库测试表.xlsx          ← R0：随包初始种子（build 时复制进 lib/assets/）
  src/services/envkit/              ← R1：runner / 契约校验 / 失败分类 / 脚本加载
  src/services/resourcekit/         ← R2：模板 / 生成器 / 校验 / 登记
  src/services/catalog.ts           ← R0：xlsx bootstrap（幂等导入）
  presets/<类别>/{profile,steps,resources,oracles}.yaml + known_issues.md   ← R2
autotest/rules/env-script-contract.md   ← R1：脚本库契约纪律（随 rules/ 索引）
```

`assets/` 落点选择 `lib/assets/`（而非 `src/assets` 直读）：`package.json` 的 `files:["lib"]`
已覆盖 pnpm 分发，`desktop/scripts/stage-server.mjs` 的 `cp(lib)` 已覆盖桌面端打包，
独立版直接从 `lib/` 运行——**三入口零额外改动即全部拿到随包资产**。代价是 build 需加一步 copy。

## 4. 阶段 R0：xlsx 自动加载 + SQLite 为唯一事实源（1–2 周）

### 4.1 设计原则

1. **xlsx 降级为"随包初始种子 + 人工增量入口"，SQLite 升为唯一事实源。**
   首次导入后一律以 SQLite 为准；xlsx 只保留两个用途：首次导入、人工导出增量。
2. **保留 `librarySheet.ts` 的单向边界**（只写"人维护的两列"，绝不覆盖 Agent 字段）——这个设计是对的，重构不破。
3. **绝不因为 bootstrap 失败就拿空库启动**（沿用 `db/sqlite.ts::adoptLegacyData` 的既有纪律）。
4. **三端共用同一个 `dataDir()` + 同一个 bootstrap 函数**，前端一律走 `/libraries` API，不直接读文件。

### 4.2 改动点（代码级）

| 文件 | 改动 |
|---|---|
| `dsh-autotest/assets/三方库测试表.xlsx` | 新增：从仓库根 `data/` 复制（349 行，git 直装与 Release tarball 都带） |
| `dsh-autotest/scripts/build-client.mjs`（或新增 `build-assets.mjs`，`build` 前置） | 构建时 `cp assets/* → lib/assets/` |
| `dsh-autotest/package.json` | `files` 保持 `["lib","cordis.patch.yml"]` 即可（已在 lib 内）；`build` 串上新步骤 |
| `dsh-autotest/src/services/catalog.ts` | **新增**：`ensureLibraryCatalog()` + `catalogStatus()` |
| `dsh-autotest/src/db/schema.ts` / `schema-sqlite.ts` | 新增 `library_catalog_imports` 表 |
| `dsh-autotest/src/db/connection.ts` | `ensureSchemaAndSeed()` 内在 `seed()` 之后调用 `ensureLibraryCatalog()`（sqlite 与 mysql 两条分支都要） |
| `dsh-autotest/src/api/http.ts` | 新增 `GET /libraries/catalog`；`/libraries/sync-sheet` 的 `apply` 语义不变，但成功后回写 import 记录 |
| `autotest/web/src/pages/Libraries.tsx` | 库管理页顶部展示"内置目录 349 行 / 已导入 348 / 问题 1（第 N 行缺地址）" |
| `dsh-autotest/scripts/verify-library-catalog.mjs` | **新增**自检，挂 `verify:all` |

### 4.3 `ensureLibraryCatalog()` 逻辑

```
resolveSheetPath()                        # 数据目录优先；没有则从随包 assets 复制一份过去
  ↓ 不存在且随包资产存在 → copy（记录 copiedFrom）
readSheet() → parseLibrarySheet()          # 复用现有纯函数：349 行逐行有交代
  ↓ 解析出 0 条 → 记 warning + 返回，不阻断启动
diffLibrarySheet(entries, loadExisting())  # 复用现有纯函数
  ↓ added / updated / unchanged / dbOnly / problems
apply=true（仅 added + updated，与手动 sync 同语义）
写 library_catalog_imports（import_id / source / sha256 / total / added / updated / problems / at）
返回 { imported, total, added, updated, unchanged, dbOnly, problems, source }
```

**幂等键**：`library_catalog_imports.sha256`。同一份表重复导入 → `added=0, updated=0`，不重复写库。

**与手动 sync 的关系**：手动 `POST /libraries/sync-sheet` 保留为"人工指定另一份表"的入口，
两者共用 `diffLibrarySheet`，差别只在 source 标记（`bundled` / `manual`）与是否写 import 记录。

### 4.4 DDL

MySQL（`schema.ts`，与既有风格一致：应用层写 ISO 时间串、无外键、显式索引）：

```sql
CREATE TABLE IF NOT EXISTS library_catalog_imports (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  source VARCHAR(16) NOT NULL DEFAULT 'bundled',   -- bundled=随包种子 / manual=人工指定
  file_path VARCHAR(512) NOT NULL DEFAULT '',
  file_sha256 CHAR(64) NOT NULL DEFAULT '',
  total INT NOT NULL DEFAULT 0,
  added INT NOT NULL DEFAULT 0,
  updated INT NOT NULL DEFAULT 0,
  unchanged INT NOT NULL DEFAULT 0,
  db_only INT NOT NULL DEFAULT 0,
  problems INT NOT NULL DEFAULT 0,
  problems_json MEDIUMTEXT NOT NULL,
  applied TINYINT NOT NULL DEFAULT 0,
  created_at VARCHAR(32) NOT NULL,
  KEY idx_catalog_sha (file_sha256),
  KEY idx_catalog_at (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

SQLite（`schema-sqlite.ts`）：`id INTEGER PRIMARY KEY AUTOINCREMENT`、`TEXT`、表级 `UNIQUE` 不用
（sha256 可重复导入，用普通索引）、`CREATE INDEX IF NOT EXISTS`。

### 4.5 API

```
GET /api/autotest/libraries/catalog
→ {
    bundled: { exists, path, sha256, total },
    latest: { at, source, total, added, updated, problems } | null,
    db: { libraries, profiled, unprofiled },
    problems: [{ row, name, reason }]
  }
```

`profiled/unprofiled` 是给 R1/R2 预留的透出（R0 阶段恒为 `0 / libraries`），
让前端从第一天就能显示"环境画像覆盖率"这个新纵轴指标。

### 4.6 R0 自检（`verify-library-catalog.mjs`，离线、无 DB 依赖的部分用纯函数）

1. 随包资产存在且可解析出 > 300 条；
2. `diffLibrarySheet` 幂等：同一份表跑两次，第二次 `added=0`；
3. 只新增不删除：库里多出的行（dbOnly）不被删；
4. **绝不覆盖 Agent 字段**：构造一个"表里有同名库、库里有 package_name"的场景，
   导入后 `package_name` 原样保留（这是整个功能的关键边界，必须有用例守着）；
5. sha256 相同 → 跳过写入；
6. 表解析出 0 条时不抛异常阻断启动；
7. 数据目录已有表时不从随包资产覆盖。

## 5. 阶段 R1：环境画像 + 脚本资产库（2–3 周）

### 5.1 脚本资产契约（核心：不让脚本库变成"自由 shell"）

脚本本体放 `dsh-autotest/scripts/env/`（Windows `.ps1` + Linux/macOS `.sh` 成对），
每条资产在 `script_library` 表 + `presets` yaml 里声明契约：

```yaml
id: build_hap
summary: 构建 HAP 安装包
entry: { windows: env/build-hap.ps1, posix: env/build-hap.sh }
inputs:
  project_dir: { type: path, required: true }
  module:      { type: string, default: entry }
  build_mode:  { type: enum, values: [debug, release], default: debug }
outputs:
  hap_path:    { type: path }          # 产物路径
  fingerprint: { type: string }        # 工具链+Sdk+依赖指纹，用于缓存命中
applies_when:
  os: [windows, linux]
  sdk_min: "4.1"
  library_kind: [ui_component, animation, storage, network, codec]
failure_taxonomy: [network, permission, sdk_version_conflict, compile_error,
                   missing_dep, device_offline, artifact_not_found]
idempotent: true
timeout_sec: 1800
approval: operator                      # 复用既有危险操作审批闸门
```

**统一 runner**（`services/envkit/runner.ts`）：


## 6. 阶段 R2：测试资源 + 预设库 + README 情报（2–3 周）

### 6.1 测试资源：三类来源，全部登记

**核心纪律：绝不让 AI 每次现场编资源。** 资源必须模板化、登记（sha256 + 大小 + schema 版本 + 来源 URL）、复用。

| 来源 | 做法 | 例 |
|---|---|---|
| 仓库自带 | clone 后扫 `**/*.json`，按 schema 特征识别 | lottie 的 demo/example `*.json` |
| 上游 canonical | 固化 URL + 版本，定期校验 | lottie-web / lottie-android 官方样本、AE 导出样例 |
| 合成生成 | 按 schema 程序化造 | 最小动画 / 空 layers / 超大 layers / 嵌套预合成 / 畸形 JSON / 编码错误 |

**lottie 的 json 资源怎么测**（用户点名场景，作为首个样板）：

json 只是输入，判据必须落在可断言的输出上：

| 维度 | 判据 |
|---|---|
| 解析正确性 | `LottieComposition` 的 layer 数 / asset 数 / duration / frameRate 与资源声明一致 |
| 帧渲染 | 首帧 / 指定帧截图 diff（复用 `oracle.ts` 的 `screenshot_diff`） |
| 异常输入 | 畸形 json 必须走 error 回调且 hilog 有错误码（`oracle.ts` 的 `hilog_keyword`） |
| 大数据 | 超大 layers 资源不崩、时长在阈值内（`automation.ts` 的 `long_running` 阈值） |

这三条直接进 `presets/animation/oracles.yaml`。

**服务器库 / CA 证书**（`resource_recipe` 类知识条目 + 脚本库条目成对）：

- `mock-server-up`：按 fixture 目录起本地 HTTP server，可注入延迟 / 状态码 / 断网
- `gen-ca`：openssl 生成自签 CA → 服务端证书 → 客户端 trust 配置 → `hdc file push` 到设备
- 资源版本化，一次构造多次复用；证书过期前 N 天自动进人工队列（运营价值）

## 10. 风险与反模式

| # | 反模式 | 防线 |
|---|---|---|
| 1 | 脚本库退化成"自由 shell"，半年没人敢改 | 强制契约 + SHA-256 锁 + 审批等级 + `verify:agent-tools` 防漂移 |
| 2 | AI 每次现场造资源，结果不可复现 | 模板化 + 登记 + 复用计数；合成必须过 schema 校验 |
| 3 | 先上向量 RAG，引入算力/外部依赖 | 保持 md + 关键词三级检索（可解释、零依赖、可 git diff）；条目过千再评估 |
| 4 | 知识库只增不清 | 沿用 deprecated 机制扩到新 kind，配工具链版本维度 |
| 5 | xlsx 回写成双向同步，冲掉 Agent 字段 | R0 自检第 4 条专门守这条边界 |
| 6 | bootstrap 失败导致空库启动 | 解析 0 条只告警不阻断；数据目录已有表不覆盖 |
| 7 | 新纵轴绕过既有闸门（审批/取消/事件） | 架构治理规则新增 `env-script-contract.md`，CI 门禁 |
