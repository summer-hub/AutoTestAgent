# 前端信息架构重构方案（R8）—— 以库为唯一主轴

> 版本：v1 · 日期：2026-10 · 状态：待评审
> 依据：对 `autotest/web/src/pages/`（20 个页面）的实测统计，而非主观印象。

---

## 1. 实测诊断（先看数据，再看结论）

### 1.1 现状盘点

当前一级导航 4 组 20 页：

| 分组 | 页面 |
|---|---|
| 工作台 | 首页、任务管理 |
| 测试资产 | 库管理、接口清单、覆盖矩阵、人工队列、知识库、测试用例、自动化脚本、环境准备、全量分析、问题归因 |
| 智能分析 | 执行计划、数据分析、归因分析、调试会话 |
| 资源与配置 | 设备管理、Prompt 管理、Agent 绑定、系统配置 |

### 1.2 三个实测事实

**事实一：65% 的页面本质都是"某个库的上下文"。**
20 个页面中有 **13 个**调用 `api.libraries`（用例/接口/覆盖/环境/归因/分析/队列/计划/任务…）。
也就是说这些页面各自带一个"选库"下拉，用户要在 13 个地方重复选同一个库。

**事实二：页面之间零互跳。**
全量检索 `location.hash` / 跨页导航：**0 处**。用户在「测试用例」看到一条失败，
想去看归因，必须回侧边栏自己找「归因分析」。**导航负担完全压在用户脑子里。**

**事实三：同一个概念被切碎在多个页面。**

| 概念 | 被切成 |
|---|---|
| 覆盖 | 接口清单 + 覆盖矩阵 + 测试用例（3 页） |
| 环境 | 库管理 + 环境准备 + 全量分析（3 页） |
| 问题 | 问题归因 + 归因分析 + 人工队列（3 页） |
| 执行 | 执行计划 + 任务管理 + 调试会话 + 设备管理（4 页） |

### 1.3 根因（一句话）

> **这个信息架构是按后端表结构组织的，不是按用户任务组织的。**
> 20 张表 ≈ 20 个页面。而用户的真实任务流是"围绕一个库，从环境→用例→执行→问题走一圈"，
> 这条路被切成了 6 个页面 + 6 次重复选库。

附带发现：`presets`（预设方案）、`script_library`（脚本资产）、`test_resources`（测试资源）
三项 R1/R2 建好的能力**有后端有 API（/env/scripts、/survey/presets、/resources），前端却没有专门入口**，
只在「环境准备」「全量分析」里露了一角——建了能力没给门，也是"耦合差"的一部分。

## 2. 重构主张：以库为唯一主轴（Library Workspace）

用户的心智模型只有一句话：**"我在处理 lottie_turbo 这个库。"**
所有事情都发生在这一上下文里。信息架构就该长成这样。

### 2.1 新结构：4 个一级区

```
┌─ 库（工作区）────────────────────┐  ← 80% 时间在这里
│  左：库列表（348 · 搜索/筛选/状态）│
│  右：该库的 Tab ──────────────── │
│     · 概览   环境健康度/覆盖率/待办/最近执行
│     · 环境   画像 + 运行记录 + 批量采集触发
│     · 用例   用例 + 脚本 + 接口面 + 覆盖矩阵
│     · 问题   工单 + 归因 + 人工队列
├─ 执行 ───────────────────────────┤
│     执行计划 · 任务 · 设备（调试会话降级为执行详情）
├─ 资产 ───────────────────────────┤
│     知识 · 预设方案 · 脚本资产 · 测试资源（1 页 4 Tab）
├─ 配置 ───────────────────────────┤
│     系统配置 · Prompt · Agent 绑定 · 数据分析
└──────────────────────────────────┘
```

### 2.2 20 个老页面的去向

| 老页面 | 新位置 | 处理方式 |
|---|---|---|
| 库管理 | 「库」左侧列表 | 改造为工作区左栏 |
| 环境准备 | 「库」/ 环境 Tab | 迁入 |
| 全量分析 | 「库」/ 环境 Tab | 迁入（批量触发入口） |
| 测试用例 | 「库」/ 用例 Tab | 迁入 |
| 自动化脚本 | 「库」/ 用例 Tab | 迁入 |
| 接口清单 | 「库」/ 用例 Tab | 迁入 |
| 覆盖矩阵 | 「库」/ 用例 Tab | 迁入 |
| 问题归因 | 「库」/ 问题 Tab | 迁入 |
| 归因分析 | 「库」/ 问题 Tab + 执行详情 | 迁入 |
| 人工队列 | 「库」/ 问题 Tab | 迁入 |
| 执行计划 | 「执行」 | 保留 |
| 任务管理 | 「执行」 | 保留 |
| 设备管理 | 「执行」 | 保留 |
| 调试会话 | 执行记录详情（不再是独立页） | 降级 |
| 知识库 | 「资产」/ 知识 Tab | 迁入 |
| Prompt 管理 | 「配置」 | 保留 |
| Agent 绑定 | 「配置」 | 保留 |
| 系统配置 | 「配置」 | 保留 |
| 数据分析 | 「配置」/ 分析（跨库聚合视角） | 迁入 |
| 首页 | **待办工作台**（重构，见 §3.2） | 重写 |

净效果：**20 页 → 4 个一级区，其中 10 个页面收进「库工作区」的 4 个 Tab。**

### 2.3 三个"补入口"（原本就没有的）

「资产」区新建三个 Tab，把已有后端能力暴露出来：

| Tab | 后端已就绪 | 用户价值 |
|---|---|---|
| 预设方案 | `GET /survey/presets`、`loadPreset` | 看到"每类库的开箱方案"，可改可沉淀 |
| 脚本资产 | `GET /env/scripts`（14 个契约） | 看到"从克隆到装包"每步干什么、失败怎么分类 |
| 测试资源 | `GET /resources` | 看到资源从哪来、复用过几次、是否临期 |

## 3. 功能耦合：把"对象关系"变成"可点的链接"

用户说的"功能之间耦合差"，解法不是把功能堆到一页，而是**建立对象链并让每跳可点**。

### 3.1 对象链（平台的核心数据关系）

```
library ──< env_profile ──< env_run ──< env_run_step
        ──< case ──< script_binding ──< execution ──< issue_ticket
        │                                        └──< attribution
        ──< api_symbol ──< coverage_matrix
        ──< knowledge_entry
```

### 3.2 每条链上的"下一步"链接（改造点）

| 当前位置 | 应能一键跳到 |
|---|---|
| 用例详情 | → 绑定脚本 → 执行记录 → 失败归因 → 提问题工单 |
| 执行记录（失败） | → 归因结论 → 该库问题 Tab → 相关知识条目 |
| 环境运行（失败步骤） | → 脚本资产契约 → 知识库同类失败 → 重新执行该步 |
| 问题工单（已验收） | → 沉淀出的知识条目 → 该库其他工单 |
| 库列表（环境标红） | → 该库环境 Tab → 最近一次失败的步骤 |
| 待办工作台任一项 | → 库工作区对应 Tab（带筛选条件） |

**判断标准：用户在任一页面产生"然后呢？"的瞬间，答案必须是一个链接，而不是侧边栏。**

### 3.3 首页重构为「待办工作台」

现在首页是统计数字堆砌（`caseOverview`/`sourceStats`），看完不知道该干什么。改为待办驱动：

```
待办工作台
├─ 3 个库环境准备失败        [去看 → 库工作区·环境]
├─ 12 条用例未绑定脚本       [去看 → 库工作区·用例]
├─ 5 个问题工单待人工验收     [去看 → 库工作区·问题]
├─ 2 个批量采集任务需 LLM     [去看 → 库工作区·环境]
└─ 最近执行：通过 86 / 失败 4  [去看 → 执行]
```

每一项都是**可点的、带筛选条件的跳转**。

## 4. 迁移路径（三阶段，不推翻、不破链接）

原则：**任何阶段老 URL（hash 深链接）都必须仍然可用**——外部可能已收藏/脚本化调用。

### Phase 1 · 双轨期（新增，不改旧）

- 新建「库工作区」页（左列表 + 右 Tab），作为新的一级入口
- 老 20 个页面**全部保留原样**
- 用户可自行选择用新工作区还是老页面
- 风险最低，可随时回退

### Phase 2 · 入口切换（老页变为跳板）

- 侧边栏改为 4 个一级区
- 老页面的一级导航项移除，但 hash 路由保留（`#cases` 仍可访问）
- 老页面顶部加"已迁入库工作区"提示 + 跳转链接
- 「资产」区三个新 Tab 上线

### Phase 3 · 链接闭环 + 清理

- §3.2 的对象链链接全部落地
- 调试会话正式降级为执行详情
- 移除已无人使用的老页面（保留路由 1 个版本过渡）
- 清理跨页重复的"选库"下拉（库工作区里不再需要）

---

## 5. 明确不做的事

| 不做 | 理由 |
|---|---|
| 不引入 react-router | 现有 hash 路由够用，且 DSH 嵌入态（iframe）依赖它；换路由库风险远大于收益 |
| 不一次性重写 20 个页面 | 风险不可控；Phase 1 双轨就是为规避这个 |
| 不按角色分页面（admin/viewer） | RBAC 已细到按钮级，再分页面是过度设计 |
| 不改变任何后端 API / 表结构 | 本次纯前端信息架构调整，后端 348 库/环境/资源能力原样复用 |

---

## 6. 验收标准

1. 用户完成一次"从发现失败到定位根因"全程**不碰侧边栏**（全部靠页内链接）；
2. 处理一个库的全流程（环境→用例→执行→问题）**只选一次库**；
3. 一级导航项从 20 个降到 4 个；
4. 老 hash 深链接（`#cases`、`#env`、`#issues` 等）100% 仍可访问；
5. `npm run verify:all` 与两个浏览器专项自检（tabbar / theme）无回归。

---

## 7. 待决策项

1. **Phase 1 是否现在就做**：建议做——双轨期无风险，且能让你先看到效果再决定后续。
2. **「库工作区」的 Tab 命名**：环境/用例/问题 三个词是否准确，有没有更好的用户语言。
3. **首页是否值得重写**：待办工作台比统计数字有用，但会砍掉一些现有信息（可先保留统计作为副栏）。
