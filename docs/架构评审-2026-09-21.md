# Agent 架构评审 — 2026-09-21

> 对象：`autotest/dsh-autotest`（服务端插件）。结论：项目本质是「用 Web 后台的思路做了一个 Agent」，而不是「用 Agent 的思路做编排」。以下按严重程度列出架构问题与改造优先级。

## 一、核心架构问题

### 1. 没有真正的 Agent Loop — 是一次性 JSON 生成，不是工具调用循环

- 位置：`src/services/executor.ts`（write_cases / update_cases / matrix_cases / explore_cases / to_script 等全部 AI 任务）。
- 现状：拼一个大 prompt → `llmJson()` 一次性要 JSON → `extractJson` 容错解析 → 入库。这是 2023 年的「prompt 出结构」模式。
- 后果：
  - 生成质量完全靠 prompt 里塞多少上下文，中途纠错只能整个重跑；
  - 「自审进化循环」（评审 Agent → 修订 → 沉淀教训）是硬编码两段式，不是模型自主的多轮决策；
  - `hdc.ts` / `hypiumGen.ts` 用**正则解析中文自然语言步骤**（`点击「X」` → 拆关键词）来执行真机操作——把本该由 LLM/tool-call 做的语义理解用 `replace()` 硬扛。步骤写法稍偏离「步骤句式契约」就全军覆没（hdc.ts 注释自述「dry-run 全军覆没」过）。

### 2. 任务执行是 fire-and-forget：没有队列、没有并发控制、没有取消

- 位置：`src/api/http.ts:1442`、`src/services/executor.ts:runTask`。
- 现状：
  - 创建任务后 `setImmediate(() => runTask(id, llm).catch(() => {}))` 直接进程内开跑，**没有任务队列**；进程重启任务直接蒸发，只能靠 reaper 30 分钟后把尸体标成 failed（`src/services/reaper.ts`）。
  - 计划执行有乐观锁抢占（`planExecutor.ts:47`：`UPDATE plans ... WHERE status <> 'running'`），但**任务没有**：`runTask` 无条件把 status 置 running，retry 接口（http.ts:1472-1473）与并发创建可以让同一任务跑两份，trace 交错。
  - 全项目没有 `AbortController` 贯穿任务执行（只有单次 LLM 调用有 60s `AbortSignal.timeout`）。用户无法取消正在跑的 AI 任务，「停止」语义不存在。

### 3. LLM 层：重试不换模型、限流是进程内存、无 token 预算

- 位置：`src/services/llmHarness.ts:87-186`（makeLlm）、`src/api/http.ts:78-88`（checkLlmRate）。
- 现状与后果：
  - makeLlm 先费力列出所有 provider/model 的 fallback 候选（`unique`），但 3 次重试**全是同一个 `preferred` 模型**，fallback 列表形同虚设；
  - 限流 `llmCalls` 是模块级数组：多节点部署（docs/deploy/multi-node.md）下形同虚设；且只挂在 API 路由上，executor 内部一次任务连环调 LLM 多次不受约束；
  - 没有按任务/按请求的 token 预算与成本记账，trace 只记字符数。

### 4. 状态持久化靠 JSON 字符串列 + 读改写，不是事件流

- 位置：`executor.ts:traceTask`、`api/http.ts:analysisProgress`。
- 现状：
  - `traceTask` 是 `SELECT trace → JSON.parse → push → UPDATE`，无任何锁；并发推进同一任务（retry + reaper + 任务自身）互相覆盖丢轨迹；
  - AI 轨迹、探索报告、执行步骤全是 JSON 字符串塞列里；分析进度是内存 Map（`analysisProgress`，完成 60s 清空、重启即丢）；
  - 做了 `listEvents` 事件表却没有成为主数据流。
- 应然：任务建模为 append-only event log，trace/进度/恢复全部从事件推导，reaper 从事件流算超时，不再「猜僵死」。

### 5. 模块级单例 + 上帝文件，与插件宿主生命周期冲突

- 位置：`src/api/http.ts`（2507 行）、`db/connection.ts`、`services/cache.ts`。
- 现状：
  - `http.ts` 内 `routes`、`llmCalls`、`analysisProgress` 全是模块级可变状态；`makeApiHandler` 每次调用会往模块级 `routes` 里重复 push，插件重载即翻倍；
  - DB 连接、缓存都是进程级单例；
  - cordis 宿主会反复 apply/dispose，目前靠 `stopAllSchedulers()` 打补丁（scheduler.ts 注释自述历史上「重载后定时任务叠加」「删除计划后 cron 永久空转」），打不全就泄漏。

### 6. 前后端是轮询架构，不是流式

- 现状：前端 2~3 秒轮询 tasks/plans；分析进度靠轮询内存 Map。
- 应然：「看 AI 干活」的产品应走 SSE/WebSocket 推 trace 增量。现在轮询 + JSON 列读改写，每个客户端都在制造竞态窗口。

### 7. 数据落点：SQLite 放在 `node_modules/dsh-autotest/data/`

- 现状：业务库写在插件包安装目录内——`pnpm install` / 升级 / 重装会直接删掉用户生产数据；README 还描述「插件数据携带了三方库、用例」——把易失目录当持久层。
- 附加：缓存失效靠手写字符串前缀（`invalidateCaseCaches`），http.ts:99-103 注释「必须在写库之后调用，否则并发读会把旧值回填」本身就是脆弱设计的自白。
- 应然：数据目录移出 node_modules，支持 `AUTOTEST_DATA_DIR` 环境变量。

## 二、改造优先级建议

| # | 改造项 | 理由 |
|---|--------|------|
| 1 | 任务队列 + worker 模型（先做进程内 FIFO + 状态抢占锁），AbortSignal 贯穿 LLM / 子进程 / hdc，任务可取消 | 解决任务蒸发、重复执行、不可停止 |
| 2 | LLM 调用改为 tool-calling agent loop：把「读仓库 / 跑 dry-run / 查覆盖矩阵 / 写用例」注册成工具，废掉中文正则步骤解析 | 「像不像 agent」的分水岭 |
| 3 | 轨迹改事件溯源，tasks 生命周期由事件推导，reaper 变为事件流超时计算 | 消除 JSON 读改写竞态与僵死猜测 |
| 4 | 数据目录移出 node_modules，可配置 `AUTOTEST_DATA_DIR` | 防升级丢生产数据 |
| 5 | LLM 重试换模型（用上 fallback 候选列表）、限流进 Redis、加 token 预算记账 | 多节点下的资源与成本治理 |
| 6 | trace 推送改 SSE，去掉轮询 | 实时性 + 消除轮询竞态窗口 |

**第一步建议**：#2（tool-calling 改造 write_cases）或 #1（队列 + 取消）。

## 三、整改进展（2026-09-21 晚）

**#1 任务队列 + 取消 —— 已完成**，落点：

- `src/services/taskLane.ts`（新）：lane = library_id，同库 FIFO 串行、跨库并行；每任务一个 AbortController；`enqueueTask / cancelTask / stopAllTaskLanes`。http.ts 的 `setImmediate(runTask)` 全部改为入队，runTask 生产调用方只剩 lane 一处。
- `executor.ts:runTask`：原子抢占锁（`UPDATE ... WHERE status <> 'running'`，照抄 planExecutor 的 claim 模式）杜绝重试/并发创建跑两份；终态更新带 `status='running'` 守卫，取消不被迟到的执行结果覆盖。
- AbortSignal 贯穿：LlmTextInput.signal → makeLlm 与 60s 超时合并（`AbortSignal.any`，低版本手动级联兜底）、abort 不重试；git 子进程（gitRepo.withGitSignal）、hdc 子进程（hdc.withDeviceSignal，ALS 模式同 connection.ts 事务上下文）；dryRunCase / exploreApp 步骤与 BFS 间隙检查取消及时收手。
- 取消 API `POST /tasks/:id/cancel` + 前端按钮；TaskStatus 新增 `cancelled`；retry 兼容 cancelled。
- reaper 启动清理扩展：遗留 pending（入队未执行）也标记中断，不再永远转圈。
- 自检：`scripts/verify-task-lane.mjs`（19 项：串行/并行/抢占锁/排队取消/运行中取消/卸载 abort/边界），已接入 `verify:all`。

**#3 轨迹改事件溯源 —— 已完成**，落点：

- `task_events` 表（`db/schema.ts` + `db/schema-sqlite.ts`）：append-only，`seq` 每任务从 1 递增，唯一键 `(task_id, seq)` 兜底；`tasks.trace` 降级为物化快照（仍是实时刷新的缓存，前端零改动）。
- `src/services/taskEvents.ts`（新）：`appendTrace / readTaskEvents(afterSeq, limit) / rebuildTraceSnapshot`。取代旧 `traceTask` 的 `SELECT trace → JSON.parse → push → UPDATE`——seq 由 `INSERT..SELECT MAX(seq)+1` 一条语句原子分配，同一任务的「追加 + 快照刷新」在进程内串行（chain），双保险下并发追加不丢不重。
- `executor.ts`：~60 个 `traceTask` 调用点零改动，只换实现体（内部 import taskEvents）。
- API：`GET /tasks/:id/events?afterSeq=&limit=` 增量读（#6 SSE 的读接口就是这一个）；`DELETE /tasks/:id` 级联删事件流。
- 快照写**故意不带 status 守卫**：取消/终态之后迟到的轨迹（「任务已取消」）必须能落进快照，否则 trace 视图看不到取消现场。
- 自检：`scripts/verify-task-events.mjs`（23 项：seq 每任务独立递增、★20 条并发追加不丢不重、快照与事件流逐条一致、afterSeq 增量读、★`LIMIT -1` 陷阱夹紧、快照可重建、终态后追加可见），已接入 `verify:all`。
- 未做的延伸：reaper 改为从事件流算超时（还靠 tasks.updated_at 猜僵死）、前端/SSE 改走 `/events` 增量读。

**#4 数据目录迁出 node_modules —— 已完成**，落点：

- 默认数据目录改为 `<安装根>/autotest-data`（安装根 = 最外层 `node_modules` 的父目录，即 DSH profile 目录；本地 checkout 退到 `$DSH_HOME/autotest/data`）。`AUTOTEST_DATA_DIR` 覆盖语义不变（自检/CI 专用，且**显式覆盖时不触发迁移**，避免把使用者真库拖进临时目录）。
- 首次启动自动搬迁旧版 `<插件包>/data`：先 `wal_checkpoint(TRUNCATE)` 并回 WAL，再整目录拷贝（`autotest.sqlite3` + `.mysql-url` + `三方库测试表.xlsx` 一个不落），旧目录改名 `data.migrated-<时间戳>` 留底。**搬不动就退回旧目录**（库被占、目标不可写、拷完没库文件），绝不拿空库启动。
- 散落的硬编码一并收口：`db/connection.ts` 的 `.mysql-url` 引导、`scripts/migrate-sqlite-to-mysql.ts` 的源库与引导文件、`librarySheet.ts` 的 xlsx 相对路径，全部改读 `dataDir()`。
- 自检：`scripts/verify-data-dir.mjs`（20 项：默认落点不含 node_modules、覆盖优先且不迁移、★旧数据一条不少、已迁过不覆盖、★失败退回旧目录、★WAL 数据不丢），已接入 `verify:all`。

**未做（仍开放）**：#2 agent loop 化、#6 SSE（读接口已就绪，缺推送）、#7 之外的单例与上帝文件拆分。

**#5 LLM 层治理 —— 已完成（2026-09-21）**，落点：

- **重试换模型**（`src/services/llmHarness.ts`）：原来费力列出所有 provider/model 的候选，3 次重试却全打在同一个 `preferred` 上。现在 `order = [首选, ...其余候选]`，`target = order[attempt % order.length]`，最多 3 次；候选不足 3 个时绕回首选（单模型部署下行为与改造前完全一致）。traceHook 与实际返回的 `provider/model` 改为当次命中的模型；失败埋点补记 `tokensIn/tokensOut`（原来漏记，会低估花费）；最终报错列出全部尝试过的模型。
- **限流全局化**（新 `src/services/llmLimit.ts` + `cache.ts` 的 `cacheIncr`）：原来的模块级 `llmCalls` 数组只在单进程有效，多节点部署下形同虚设（插件重载还会翻倍累计）。现在 Redis 可用时用 `INCR` + 首次 `PEXPIRE` 做固定窗口全局计数（键 `autotest:llmrl:<分钟桶>`），不可用时退回进程内滑动窗口。`PEXPIRE` 续不上会**删键并放弃 Redis 计数**——否则无 TTL 的窗口键会永远留在 Redis 里，把这个限流项永久卡死。
- **单任务 token 预算**（新 `src/services/tokenBudget.ts`）：事实来源就是 `agent_events`（埋点本来就写 `tokens_in/tokens_out`，`(task_id, created_at)` 有索引），不另存状态 → 重启 / 重试 / 多节点共享 MySQL 时账目天然一致，也不需要清理钩子。新设置 `agent.maxTokensPerTask`（默认 300000，0=不限制），`makeLlm` 每次调用前检查，超限直接抛错让任务失败留痕。
- **关键决策：限流计数仍只挂在 API 入口**（`{ llm: true }` 路由）。一次任务内部会连环调十几次模型，按分钟条数卡会让任务直接失败——那部分成本交给 token 预算管。两者分工：分钟条数防"人刷"，token 预算防"任务烧"。
- 自检：`scripts/verify-llm-fallback.mjs`（31 项：★ 重试跨模型轮转与首选打头/去重、DSH 默认模型的对象字面量不重复计数、★ 单/双候选绕回首选、取消不换模型重试、★ 成功与失败埋点都记 token、★ 超预算零调用、预算 0 与按任务隔离、限流进程内回退、★ **Redis 全局计数用两个子进程验证：第二个节点被第一个节点的计数挡住**），已接入 `verify:all`。Redis 用一个内存假 RESP 服务（真解析 INCR/PEXPIRE），不依赖外部 Redis。
