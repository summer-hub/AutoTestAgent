# 修复记录 2026-09-12 — 第一批 P0/P1 稳固性修复

> 本文记录本轮修复的**问题、根因、改法与验证方式**。所有结论均可在 `npm run verify:all` 中复现。
> 审计来源：对 `autotest/dsh-autotest/src`、`autotest/web/src` 的逐文件审查 + 本机实测。

## 怎么验证

```bash
cd autotest
npm run typecheck     # web + 插件 类型检查（此前 CI 完全没有这道门禁）
npm run verify:all    # 构建 + 三套自检，全部离线可跑（不连 MySQL、不调 LLM、无设备自动跳过真机组）
```

新增的两套自检脚本：

| 脚本 | 覆盖 |
|---|---|
| `dsh-autotest/scripts/verify-data-integrity.mjs` | 事务隔离、事务串行、归档列对齐、种子配置、密钥脱敏、运行态生命周期、`llmJson` 并发隔离 |

## P0：会造成静默数据丢失 / 功能不可用

### 1. SQLite 模式事务隔离被击穿（最严重）

- **现象**：事务外的并发写入会被卷进别人的事务并**一起 ROLLBACK**；两个交叠事务直接把第二个打成 500。
- **根因**：`db/connection.ts` 的 `query()` 在 SQLite 分支**永远使用那一条全局连接**，而 `transaction()` 只是对同一张连接 `BEGIN IMMEDIATE`。better-sqlite3 是单连接 + 同步执行，事务打开期间其他请求发来的语句自然落进同一事务。
- **改法**：加一把异步互斥锁 `sqliteTxStore/acquireSqliteTx/releaseSqliteTx`：
  - 事务外发起的语句先 `while (sqliteTxOpen) await sqliteIdleTick()` —— 循环条件同步检查、退出后同步执行语句，**中间不留 await 缺口**；
  - 事务之间串行；嵌套 `transaction()` 并入外层（避免自我死锁）。
- **踩坑记录**：第一版把"检查 + 置位"拆在 `await` 两侧，结果三个并发调用都以为自己拿到了锁，自检立刻报出 `cannot start a transaction within a transaction`。这正是先写自检的价值。
- **验证**：`verify-data-integrity.mjs` 的「事务隔离 / 事务串行」两组（5 项）。

### 2. 夜间归档必然失败，执行记录永不归档

- **现象**：每日 03:00 的归档任务抛错，`executions` 无限增长，只在日志留一行错误。
- **根因**：`executions_archive` 比 `executions` **少一列 `trace_id`**（`trace_id` 是后来只给主表补的），而 `archive.ts` 用的是 `SELECT *` 隐式列序。
- **改法**：两张 schema 都补上 `trace_id`；SQLite/MySQL 两条迁移清单都补 `executions_archive.trace_id`；`archive.ts` 改为**显式列清单** `ARCHIVE_COLUMNS`，列漂移今后会在自检里被抓住而不是静默报错。
- **验证**：`verify-data-integrity.mjs` 的「归档链路」组，真插一条 1 年前记录并真跑一次归档。

### 3. 工作区被种子写死为开发机路径

- **现象**：`data/seed.ts` 把 `app.workspace` 种成 `"D:\autotest\workspace"`。换机器/换系统后工作区指向无效目录；更糟的是 `workspaceConfigured()` 返回 true，**"未配置工作区"的告警被彻底架空**（工作区治理逻辑失效）。
- **改法**：种子里删掉这个键（默认值本来就是空）；`workspaceNotice()` 增加"命中旧种子默认值"的提示；启动时打印该提示；系统配置页把它渲染出来。
  - 刻意**不**自动改写已有数据：该目录下可能已有真实仓库/脚本，静默清空会让平台看起来"数据全没了"。
- **验证**：`verify-data-integrity.mjs`「种子配置」组；UI 提示为人工可验。

### 4. 明文密钥出现在无鉴权 API 响应

- **现象**：`GET /settings` 回传 `db.mysqlUrl`（含数据库口令）；`GET /models` 回传 `api_key` 明文。
- **改法**：新增 `services/secrets.ts`（`maskSecret` / `maskUrlPassword` / `isMaskedSecret` / `resolveSecretInput`）：
  - URL 型凭据只给口令段打码，保留 host/库名可读性；
  - `mapModel` 只回传掩码 + `hasApiKey` 布尔（前端状态点改用它）；
  - **防回写**：入参若等于掩码则视为"不改动"，绝不用 `••••` 覆盖真实凭据；显式空串仍可清空。
- **验证**：`verify-api-guard.mjs`「出参脱敏」组（7 项）+ `verify-data-integrity.mjs`「密钥脱敏」组（10 项）。

### 5. 新建 Prompt 模板 100% 失败

- **根因**：`Prompts.tsx` 新建时用 `{ id: 0 }` 哨兵对象，保存却判 `if (editing)`（对象恒真）→ `PUT /prompts/0` → 404。
- **改法**：改判 `editing.id > 0`。
- **验证**：`verify-api-guard.mjs`「Prompt 模板」组（新建 200 / `PUT /prompts/0` 404 / 更新 200）。

### 6. 计划异常后永久卡在 running

- **现象**：`executePlan` 无 try/catch，`JSON.parse(device_ids)` 等前置解析一旦抛错，计划永远停在 running；调用侧还用 `.catch(() => {})` 把异常彻底吞掉，前端每 2 秒轮询一个不会结束的状态。
- **改法**：
  - `executePlan` 拆成「原子占位 + try/catch 包住主体」：占位用 `UPDATE ... WHERE id=? AND status <> 'running'`，`changes=0` 即说明已有实例在跑（**顺带修掉连点两次/cron 与手动重叠时同计划跑两份**）；
  - 抛出的异常必定写 `status='failed'` 并记录原因；
  - 新增 `services/reaper.ts`：启动时清理上次进程遗留的 running；每 5 分钟按"空闲 30 分钟"阈值清理僵死状态（正在推进的计划每步都会刷新 `updated_at`，不会被误杀）。
- **验证**：`verify-data-integrity.mjs`「运行态生命周期」组（7 项，含"前置解析抛异常仍落到 failed"）。

## 顺带清理的失实项

- **死旋钮**：`device.execEngine` 与 `exec.scriptMode` 在设置页可选，但**全仓库没有任何代码读取它们**（`grep` 确认只有默认值声明）。已从 `SETTING_DEFAULTS`、设置页、种子里移除——留着会让用户以为改了行为。README 中对应的"无设备自动回退模拟"描述同步删除（真实行为是直接失败并写明原因）。
- **README 数字**：原文写"注册 400+ 真实三方库 / 4.5 万用例 / M1 45,700 用例 70,852 版本记录"，而种子只注册 1 个示例库、线上实测 2 库 1 用例。已改为与实现一致，并把"分表路由（library_id % 16）"标注为**预留未启用**（`caseTableFor()` 恒返回 `cases`）。
- **版本号**：`autotest/README.md` 里的 `v0.1.27` 与包版本 0.1.56 相差 29 个版本，已修正并补上"发布前先构建"的步骤（`build:plugin` 此前不含 `build:embed`，改完前端不重建也能打包）。

## 尚未处理（下一批候选）

以下为审计已确认、本轮**未**改动的问题，按建议优先级排列：

1. `http.ts` 仍是一个 1700+ 行的单文件（71 条路由 + 表驱动 + 全部判参）；建议按域拆分 `api/routes/*`，引入 schema 校验层与 presenters。
2. `GET /libraries` 的 `page` 与 `cursor` 混用会导致第 2 页倒序重复；建议统一为 keyset 分页。
3. `executions_archive` 之外的 `agent_events` 无保留期策略，只增不删。
4. MySQL 每次启动无条件执行 8 条 `ALTER TABLE`，且没有 `schema_migrations` 表；建议引入编号迁移。
5. 执行层：任务不可取消（全链无 `AbortSignal`）、`traceTask` 读-改-写在并发分片下丢轨迹、设备无租约锁、失败工件（截图/报告）未入库、无 JUnit/HTML 报告与 CI 集成。
6. 设备自动化：`hdc.ts` 的 Android XML 正则强制 `class` 出现在 `bounds` 之后（标准 uiautomator dump 恒 0 命中）、`dumpMode` 进程级缓存一次失败即永久切模式、`findKeyword` 取首个子串匹配且未命中仍报通过——存在"绿色假通过"。
7. 前端：`Cases.tsx` 请求乱序覆盖、筛选不重置页码、无空态；无 toast/全局加载态；无键盘可达性与 i18n。
8. `db/init.ts` 不建表（`npm run db:init` 在空库上无效）；`scripts/clean-stale-tasks.mjs` 指向了错误的库文件名且硬编码绝对路径（已被 reaper 取代，建议删除）。
