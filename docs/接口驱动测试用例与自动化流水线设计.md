## 0. 结论摘要

当前两个 Agent（真机遍历生成用例、用例优化）的缺陷**不是提示词没调好，而是两条设计约束决定的**：

1. **遍历引擎在采集阶段就丢控件**：候选必须带可见文本、按 label 去重、深度硬上限 2、下拉/输入无专项交互。
2. **生成引擎完全不知道库的对外接口**：喂给 LLM 的上下文只有"每页的控件文本列表"，因此只能产出点击剧本，不能产出接口契约用例。
3. **优化引擎只能改写、不能补缺**：用例数量不足这件事，在优化环节原理上无法解决。

本设计的核心改动是**把"UI 驱动"换成"接口面驱动"**：先建立「对外接口 ↔ demo 覆盖 ↔ 真机控件」三者的矩阵，再由矩阵驱动用例生成，四类场景（正向 / 空值 / 边界异常 / 大数据）逐接口展开；每条用例判定 demo 可测性（开箱可测 / 改参数可测 / 需改代码 / 无法测），需改代码的产出**可评审的最小补丁草案**；无法测的进入**人工接管队列**，人工确认后的结论沉淀为 **LLM wiki 知识条目**（纯文件 + 关键词检索，不依赖显卡）。

外部依赖已核实：`deveco-cli`（`@deveco/deveco-cli`，openharmony-sig）把 `ohpm/hvigor/hdc/emulator/hilog` 统一封装，并提供 `ui layout`（带节点 ID 与 `clickable/longClickable/scrollable/checkable` 标志）、`ui click --id`、`check lint/compat`、`docs search/read`、`device sqlite3`、`skills add`、`serve mcp`。**这正是本设计缺失的工具层**，且能把"无文本控件丢失""靠坐标点击"两个硬伤直接消除。

### 0.1 工具链核实结论（2026-09-12 实测，**优先于下文任何命令表述**）

在开发机（Windows，`devecocli` 1.3.2）上逐条实测，结论如下——**下文凡与本节冲突的，以本节为准**：

| 结论 | 证据 | 对设计的影响 |
|---|---|---|
| ❌ **`check arkts` 不存在** | `devecocli check --help` 只列出 `compat`、`lint` | 原设计把 `check arkts` 当作 demo 补丁的语法校验门禁，**该门禁不存在**；相关章节（§3.4、§6.x、§7.x、§9）已标注作废 |
| ❌ **`check lint` 在本机对 OpenHarmony 工程是"假通过"** | `devecocli check lint entry/src/main/ets` → **exit 0** + `No defects found. … Files checked: 0`，stderr 仅 `Some error occurred during linting`（错误被吞） | **绝不能作为补丁/AI 产物的验收判据**：它检查 0 个文件却报"无缺陷" |
| 🔍 根因：命令行工具与工程类型不匹配 | 直接调用其底层 `codelinter`（`D:\huawei\command-line-tools\bin\codelinter.bat`，6.0.240）得到明确报错：`The type of command line tools does not match that of the project. Use the command line tools intended for OpenHarmony projects.`（本机只装了 **HarmonyOS 版** command-line-tools，而 tpc_samples 工程 `runtimeOS: "OpenHarmony"`） | 需要对 OpenHarmony 工程单独安装对应风味的工具链；**版本/风味不匹配时必须报错而不是静默通过** |
| ⚠️ 即使风味匹配、依赖装齐、并**故意植入坏代码**，报告仍为空 | 副本工程改 `runtimeOS: "HarmonyOS"` + `ohpm install --all` + 新增含 `no-var`/`no-explicit-any`/`no-unused-vars` 的 `.ets` 文件 → `codelinter` 进度 100%、`[]` 空报告 | 静态检查在当前环境**尚不可用**；任何静态检查接入都必须先过"正面对照"（见下） |
| ⚠️ `check compat` 必须显式给版本 | 不给 `--source-version/--target-version` 时报错；`docs search` 走本地文档目录，**不需要登录**（`auth status` 为 `Not logged in` 仍可用） | 矩阵"风险"列可用，但命令要写全参数 |
| ✅ `ui layout --device <serial>` 可用 | 真机 dump 出锁屏节点树 | UI 采集路线成立 |

**新增的硬性纪律（已落进自检）**：任何"静态检查/构建"类判据接入前，必须通过**正面对照**——向被测工程注入一个必然违规的文件，若工具报"无缺陷"，则该工具判定为**不可用**，不得作为门禁；宁可标注"未经静态校验"，也不能拿它当绿灯。这条纪律与"假通过=0"是同一件事的两面。

**运行期依赖（已落进自检 `verify:oracle-runtime`）**：Hypium 脚本必须用**装了 hypium 的解释器**运行。本机 `python` = 3.13.15（**没有 hypium**），hypium 6.1.0.210 只装在 `D:\Programs\Python\Python310`，故正确命令是 `py -3.10 main.py <module>`（或 `AUTOTEST_PYTHON` 指定）。

## 1. 背景与问题

### 1.1 用户可观察到的现象

- 遍历没有覆盖全部页面与子页面；按钮、下拉框、输入框等控件采集不全。
- 生成的用例数量偏少。
- 用例缺少接口语义层面的验证（不知道库到底对外暴露了什么、哪些没被测到）。

### 1.2 代码级根因

| # | 现象 | 根因 | 位置 |
|---|---|---|---|
| R1 | 子页面的子页面完全没进 | `maxDepth` 默认 2；`depth >= maxDepth` 的页面 `isLeaf=true`，只采集不点击 | `services/uiExplorer.ts:161,282` |
| R2 | 一整类控件从未出现 | 候选过滤要求 `(text \|\| desc).trim()` 非空 → 图标按钮/图片按钮/无文字控件既不进清单也不被点击 | `services/uiExplorer.ts:333-336` |
| R3 | 下拉框选项枚举不到 | 点开后只做 `entered` 判定，`dumpCurrent()` 的节点**不回填 inventory**；下拉项非独立页面 → 判为"未进入" | `services/uiExplorer.ts:347-364` |
| R4 | 同名控件只采到第一个 | `seenLabels` / `clickedLabels` 仅按 `label.slice(0,24)` 去重，且 `seenLabels` 跨视口共享 | `services/uiExplorer.ts:307,339-341,349-350` |
| R5 | 同一页不同状态被合并 | `entered` 要求页面签名未被访问过 → Tab 切换、展开/折叠、登录前后只留一份 | `services/uiExplorer.ts:361` |
| R6 | 每页控件上限名不副实 | 首页用 `controlsPerPage`(默认 12)，子页用硬编码 `FULL_CONTROLS_CAP=60`，点击上限 `CLICK_CAP=100` | `services/uiExplorer.ts:264,271,273,370,400` |
| R7 | 用例数量偏少 | 生成配额 = 每页 1~2 条，入库上限 `max(20, 页数×2)` | `services/executor.ts` exploreCases |
| R8 | 用例不验证接口语义 | 送给 LLM 的页面上下文只有 `{path, controls:[文本], swipes, scrolls, animation}` | `services/executor.ts:758-764` |
| R9 | 臆造的预期照样入库 | guardrail 只校验控件引用存在性；**验证类步骤豁免**、**无 pagePath 直接放行** | `api/http.ts` validateDraftsAgainstPages |
| R10 | 优化补不了覆盖缺口 | `optimizeCaseById` 只能改写既有用例 | `services/executor.ts` |
| R11 | 无控件的页面静默丢数据 | `parseNodes` 的 JSON 分支解析失败返回 `[]`，调用方无法区分"空页面"与"解析失败" | `services/hdc.ts:197-202` |
| R12 | 生成脚本可能是假通过 | `stepToPython` 未映射的步骤生成注释行；空步骤脚本只产出 `wait(2)` 却被判 passed | `services/hypiumGen.ts` |

R2/R3/R4 是**采集规则**导致的整类丢失；R8/R9 是**上下文与校验**导致的语义缺失。这四条解释了用户观察到的绝大部分现象。

### 1.3 结论

需要新增加的不是"更多提示词"，而是三样东西：

1. **一个可信的遍历层**（能回答"发现多少、点击多少、收录多少、为什么没点"）；
2. **一个接口面事实来源**（库到底导出了什么，demo 到底用了什么）；
3. **每一条用例的可执行性判定**（能不能自动跑、不能的话谁来做、怎么做）。

## 2. 设计目标与非目标

### 2.1 目标（可度量）

| 编号 | 目标 | 度量方式 |
|---|---|---|
| G1 | 遍历结果可解释 | 每次遍历产出覆盖率报告：发现 N / 点击 M / 收录 K / 未处理原因分布；`N-K` 的每条原因可见 |
| G2 | 接口面完备 | 每个导出符号在矩阵中占一行，含来源文件与行号；未覆盖项显式标记 |
| G3 | 用例按场景维度展开 | 每个导出接口 `≥1 正向`，并按适用性矩阵补齐 `空值 / 边界异常 / 大数据` |
| G4 | 每条用例可执行或可解释 | 100% 用例带 `testability` 判定（A/B/C/D）与理由；C 类带补丁草案 |
| G5 | 预期结果机器可校验 | 100% 用例带 `oracle` 字段（至少一项：控件文本 / hilog 关键字 / 动画状态 / 返回值展示 / 截图差异） |
| G6 | 人工介入有闭环 | 人工接管队列可查询、可分派、可回填结论；回填后触发下游重跑 |
| G7 | 用例与脚本双向可追溯 | 手工用例 → 脚本映射可查；手工用例升版时提示受影响脚本 |
| G8 | 知识可沉淀可复用 | 人工确认的结论以结构化条目入库，并在后续同类任务中被检索引用 |

### 2.2 非目标（明确不做）

- **不做 UI 状态的完全覆盖**：状态 × 数据 × 时序组合爆炸，无法穷尽。覆盖以"可达页面 + 已声明接口维度"为边界，超出部分显式列入"未覆盖原因"而不是假装覆盖。
- **不做接口行为的自动判定**（无 oracle 时）：库是否"有 bug"需要参照物。系统只输出"异常信号 + 证据"，判定权交给人。
- **不做动画/视频内容的自动判定**：交由人工或帧差工具，进入人工接管队列。
- **不引入向量数据库/嵌入模型**（见 §7.1 的量化理由）。
- **不修改用户仓库**：所有 demo 改造在**独立副本**上进行（见 §10.3）。

## 3. 外部依赖调研结论

### 3.1 `deveco-cli`：本设计的工具层

来源：`https://gitcode.com/openharmony-sig/deveco-cli`（npm `@deveco/deveco-cli`，MIT）。
封装了 DevEco Studio 工具链（`ohpm` / `hvigor` / `hdc` / `emulator` / `hilog`），并提供技能安装、工程脚手架、本地文档检索与 MCP 服务。

对本设计有直接价值的命令（均来自其 README）：

| 命令 | 能力 | 在本设计中承担 |
|---|---|---|
| `ui layout --format json` | 导出 UI 节点树：**类型 / 节点 ID / bounds[left,top,right,bottom] / 文本 / `clickable` `longClickable` `scrollable` `checkable`**；`--mode simplified` 折叠无意义包装节点；`--depth`、`--all-windows`、`--window` | **替换 `hdc.uiDump + parseNodes`**。解决 R2（用 `clickable` 而非"有文本"判定候选）、R11（结构化输出，解析失败不再与空页面混淆） |
| `ui click/doubleclick/longclick/swipe/fling/drag/dircfling/text --id` | 交互原语，`--id` 自动解析为中心坐标 | 替代坐标点击（R4 的坐标脆弱性、以及"重放路径"失效问题） |
| `ui window list --all` | 窗口列表（窗口 ID / 名称 / PID / 聚焦态） | 多窗口、弹窗、悬浮窗场景的采集与切窗 |
| `ui screenshot` | 截图 | oracle 的一种（截图差异）、失败证据留存 |
| ~~`check arkts [files] [--fix]`~~ **（已核实不存在，见 §0.1）** | — | **不可用**：`devecocli check --help` 只列出 `compat` 与 `lint` 两个子命令，没有 `arkts`。原文来自对 CLI 的错误假设 |
| `check lint [path] --format json` | Code Linter 包装（转调 `codelinter`） | ⚠️ **本机不可用作判据**：对 OpenHarmony 工程直接报 `Files checked: 0` 却 exit 0，见 §0.1。**绝不能拿它当补丁校验门禁** |
| `check compat --source-version --target-version --format json` | 基于 `apkanalyzer-apiscan` 的**跨 SDK 版本 API 变更扫描** | 矩阵"风险"列：接口在新版本被废弃/签名变更/行为变更 |
| `docs search <kw> --catalog harmonyos-references --format json` / `docs read <id>` / `docs catalog` | **本地 HarmonyOS 官方文档检索**（版本说明/指南/API 参考/最佳实践/FAQ/变更预告） | **oracle 的主要来源**：接口契约、参数取值范围、异常语义 |
| `device list/view/file/sqlite3` | 设备信息、设备文件系统、设备侧 sqlite3 | "外接数据库"类场景的判定与执行；dumpsys/DB 校验 |
| `emulator list/start/stop/create/image/license` + 场景操作（`shake`/`rotate`/`fold`/`battery`/`geolocation`/`scene`/`sensor`） | 模拟器管理与**设备状态注入** | 无真机时的替代；更重要的是**可复现地构造边界场景**（电量、折叠态、传感器、地理位） |
| `run --apply <changes.txt>` / `run --hotreload [action]` / `run --hotreload-apply <changes.txt>` | 快速增量部署与热重载：`--apply` 只重编改动文件（改动清单来自 `.hvigor/`，每行一个相对工程根路径；前提 DevEco Studio ≥ 6.1.1 且先跑过一次全量 `run`）；`--hotreload` 需常驻进程，`stop` 释放 | C 类补丁的**快速验证**（避免每次全量构建） |
| `build [--module]` / `build clean` | hvigor 构建 | demo 改动的构建与产物路径 |
| `run [--device] [--ability] [--module]` | 构建 + 安装 + 启动 | 用例前置：拉起被测应用并进入指定 Ability |
| `log [--level E]` | hilog 读取 | **异常信号的主要来源**；oracle 的一种 |
| `skills list/find/add/remove` + `init --agent/--mcp/--skill` | 技能安装到指定智能体；MCP 服务配置 | §8 Agent 绑定与外部 agent 互操作 |
| `serve mcp` / `serve lsp` | MCP / LSP 服务 | 插件工具面的对外暴露与编辑器集成 |

> **关键影响**：`ui layout` 输出的 `clickable/longClickable/scrollable/checkable` 与**节点 ID**，让"候选集合"不再依赖可见文本，且交互可以用稳定 ID 而不是坐标。这一条同时消除了 R2 与 R4 的技术前提。

### 3.2 `deveco-code`：可选的对等 Agent

来源：`https://gitcode.com/openharmony-sig/deveco-code`（npm `@deveco/deveco-code`，MIT）。
定位：**面向 HarmonyOS 开发的终端 AI Agent**，基于开源项目 **OpenCode** 扩展，保留 Provider / MCP / Skill / Plugin 体系。

已知事实：

- 平台：macOS(arm/x64) 与 Windows，**暂不支持 Linux**。
- 前置：Node ≥ 22；DevEco Studio **≥ 6.1**（编译构建/模拟器/真机调试需要）与 `DEVECO_HOME` 环境变量。
- **需要华为账号登录**（`deveco auth login`）；登录后可用内置免费模型通道（GLM-5.1，默认 50 次/分钟），也可通过 `deveco.jsonc` 配置第三方 Provider。
- 内置 `serve`（HTTP 服务）、`mcp`（MCP 服务）、`agent`、`stats` 等子命令；工程内使用 `.opencode/agent/*.md`、`.opencode/command/*.md` 定义自定义 agent 与命令。

在本设计中的定位：**它不是必须依赖**，而是"用户可替换 Agent"的一种实现。两种集成方式（优先级从高到低）：

1. **MCP / serve 互操作**（推荐，待 spike 验证）：`deveco serve` 或 `deveco mcp` 暴露能力，AutoTest 以 MCP client 身份调用；
2. **CLI 一次性调用**（保底）：若存在非交互入口，则以受限 prompt 调用并收集 diff。

> **待验证（必须在 P5 之前 spike）**：`deveco-code` 的非交互执行入口是否存在及其确切的参数形式。**本设计不依赖它**——所有 C 类补丁的生成都先走"内置 Agent 出 diff 草案"，deveco-code 仅作为可选增强。
>
> ⚠️ 原文此处写的是"`check arkts` 校验"，但 **`check arkts` 已核实不存在**（§0.1）。P5 的补丁校验因此**降级为**：① 补丁必须能干净应用（唯一子串匹配，见 `testability.ts`）；② 应用后由人评审；③ 除非接上一个**通过正面对照**的静态检查，否则标记"未经静态校验"。

### 3.4 降级路径（deveco 工具不可用时）

设计不得变成"没有 deveco-cli 就完全不能用"。每个依赖点都要有降级：

| 能力 | 主路径 | 降级路径 |

| 静态检查 | ~~`devecocli check arkts`~~ 已核实不存在；`check lint` 本机对 OH 工程**检查 0 个文件却 exit 0**（§0.1） | 跳过，补丁草案标记为"未经静态校验"（**这是当前唯一诚实的默认**） |
| 设备状态注入 | `devecocli emulator ...` | 真机手动物理操作（进入人工接管队列） |

### 5.3 库清单的两个数据源：xlsx（人）与 db（Agent）

项目里存在两份"库清单"，必须先定清楚谁是谁的事实来源，否则同步一次就会把对方的数据洗掉。

| 数据源 | 维护者 | 负责的字段 | 说明 |
|---|---|---|---|
| `三方库测试表.xlsx` | **人** | 库名、仓库地址（含 `/tree/<分支>/<子目录>`）、子目录 | 269 行的业务清单，人用 Excel 增删改 |
| `libraries`（db） | **Agent** | `package_name`、`main_ability`、`last_commit`、`current_version`、`last_synced_at`、`status` | 真机遍历/执行时自动识别与回填的"运行时事实" |

**同步语义（单向 xlsx → db）**：

- 只写人维护的三列（库名 = 匹配键、`repo_url`、`repo_subpath`）；**绝不覆盖** `package_name` / `main_ability` / 同步状态；
- 匹配键是**库名**（实测 269 行里库名唯一、无重名；URL 反而有 5 组重复 —— 一个 demo 可以覆盖多个库，所以 URL 不能当键）；
- **绝不删除**：库表里有、表里没有的库只进 `dbOnly` 报告（删库会级联删用例/任务/执行历史）；
- 必须**先预览再执行**：`applied=false` 返回完整差异（新增/更新/无变化/库中独有/问题行），人确认后才落库；
- 必须**幂等**：同步一次后再同步，结果必须是 0 新增 0 更新，否则人无法用 `updated` 判断"表到底改了什么"；
- 脏行**逐行报告行号**：缺库名、重名、缺 URL、非 http(s)、库名超长、人加的合计行 —— 静默少几行在 269 行的表里没人会发现；
- 反向导出只写**另一个文件**（`三方库测试表.库状态回写.xlsx`），永远不改人维护的那份表。

> 这条边界有专门的离线套件（`verify-library-sheet.mjs`，纯解析/差异函数）与 API 级断言（`verify-api-guard.mjs` 里"★ Agent 补的包名与入口 Ability 没被同步冲掉"）。**改动同步逻辑时必须保持这两处通过。**

## 6. 阶段详设

### 6.1 S1/P1 · 遍历可信化

**目标**：把"漏了什么"变成可数、可解释的数字。

改动点：

1. **候选集合改为"可交互节点"**，不再要求有文本：
   ```
   候选 = 节点 where (clickable || longClickable || scrollable || checkable || 有 text/desc)
          且 bounds 在内容区（排除状态栏/导航条）
   ```
   无文本节点用 `(id, type, 坐标桶)` 做标识 —— 这依赖 `ui layout` 提供的**节点 ID**。
2. **去重键从 label 改为 `(id 或 type, 坐标桶)`**：同屏同名控件不再互相吞掉（修 R4）。
3. **控件分类专项交互**（修 R3）：
   | 控件类型 | 交互序列 | 期望采集 |
   |---|---|---|
   | Button/可点击文本 | tap → dump → 判断是否新页 → 必要时返回 | 目标页控件 |
   | TextInput | tap → 输入（正向/空值/超长/特殊字符）→ dump → 校验提示 → 清空 | 输入校验提示、错误态 |
   | Dropdown/Select | tap → **dump 展开态并回填 inventory** → 逐项 tap 采集 → 关闭还原 | 选项清单、选择结果 |
   | Checkbox/Switch | tap ×2（开/关）→ 记录两种状态 | 状态双向、状态文案 |
   | Scrollable 容器 | 逐屏滑动至底部（含"已到底"判定）→ 记录总屏数 | 长列表（大数据场景的前置） |
   | Tab/Segmented | 逐 Tab 切换 → 每 Tab 单独作为状态采集（修 R5） | 各 Tab 内容 |
4. **深度策略改为预算制**：`maxPages` / 单页时间预算 / 总时间预算 / 设备停留步数任一耗尽即停；`maxDepth` 降级为**排序偏好**（广度优先），不再是硬闸（修 R1）。
5. **状态化页面标识**：页面签名叠加"状态指纹"（Tab 索引、展开项、开关态），使同一路由的不同状态各自成页（修 R5）。
6. **覆盖率报告**（新增产物）：
   ```json
   {
     "pages": 37, "pagesBudgetSkipped": 6,
     "controls": { "discovered": 412, "clicked": 380, "collected": 396, "skipped": 16 },
     "skippedReasons": { "budget": 6, "duplicate": 5, "notInteractive": 3, "blockedByModal": 2 },
     "unparsedDumps": 0,
     "hilogErrors": 4
   }
   ```
   报告随遍历一起入库，前端可视化；**`unparsedDumps > 0` 必须显式告警**（修 R11）。
7. **同步修正设置项语义**：`explore.controlsPerPage` 要么统一生效，要么从设置页移除（避免"改了没效果"）。

**验收**：给定 demo 工程，遍历产出报告且 `discovered - collected` 的每条原因可追溯；人为埋一个无文本图标按钮与一个下拉框，二者都被采集。

### 6.2 S2/P2 · 接口面提取

**输入**：三方库仓库（或已编译的 HAR/HSP）。

**提取顺序**（按可靠性降序，命中即用，全部命中则合并去重）：

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | **HAR/HSP 产物中的 `.d.ets` / `index.d.ts`** | 编译产物是权威接口面；`build` 后可得到 |
| 2 | `library/Index.ets` 及其导出链 | 源码形态的入口，逐层解析 `export` |
| 3 | `oh-package.json5` | 包名、版本、依赖、`main`/`types` 入口 |
| 4 | 源码目录扫描 | 兜底：`export class/function/interface/enum/const` |

**每个符号抽取**：名称、种类、签名、参数（名/类型/可选/默认值）、返回类型、声明的异常、`since`、`deprecated`、声明文件与行号、JSDoc/注释。

**oracle 补强**：对每个符号执行
```
devecocli docs search "<符号名>" --catalog harmonyos-references --format json --limit 5
→ 命中则 docs read <id> 取全文 → 抽取：参数取值范围、错误码、异常语义、注意事项
```
这一步是"异常处理没考虑全"这个需求的**事实依据来源**。

**风险标注**：
- `devecocli check compat --source-version <当前> --target-version <目标> --format json` → 标记签名/行为变更、废弃接口。

**输出**：`api_symbols` 表 + 一份人可读的《接口清单.md》。

#### 6.2.1 P2 实现后按真实仓库修正的结论（json-schema，已实现并跑通）

设计稿是按"标准 ArkTS 库工程"写的，真实仓库（`openharmony_tpc_samples/json-schema`）与之有四处关键差异，
下面的修正都已落到代码里，不按这个来会**静默漏符号**或**报出假覆盖**：

1. **入口不在 `library/Index.ets`，而在清单里**。该库入口是 `library/oh-package.json5` 的
   `"main": "index.ts"`（`types` 为空串）。所以入口解析顺序是：`oh-package.json5` 的
   `types` → `main` → 约定文件名。**必须用清单**，凭文件名猜会在真实仓库上直接失败。

2. **编译产物经常不存在**。`build/` 被 gitignore，仓库里没有 `.d.ets` / `index.d.ts`，
   只有构建后才有。因此"HAR 产物优先"这条实际很少命中，源码 export 链才是主力路径。

3. **真实源码是打包产物**。`library/index.ts` 是纯 re-export 桶，指向一个 7680 行的
   CommonJS 拼装文件：定义形态是 `var Validator = function Validator() {}` +
   `Validator.prototype.addError = function(...)` + 末尾 `export { origincode_5 as SchemaError, ... }`。
   提取实现必须支持：多行 `export {...} from`、`export type {...}` 与值导出分开、
   `a as B` 别名、`export *`、`exports.X =` / `module.exports.X =`，以及原型方法 →
   判为"类"并把方法清单单独存一列（class 类符号真正可测的单元是它的方法）。

4. **类型信息只存在于 JSDoc**。JS 打包产物里没有类型标注，`@param {object} x` /
   `@returns {object}` / `@throws {SchemaError}` 是唯一的类型来源；`[options]` 才是可选性依据。
   参数解析必须把 JSDoc 合并进来，否则参数全是光秃秃的名字。

**假覆盖的三个陷阱**（本项目硬门槛是"假通过 0"，这三条都会把"没测"报成"测了"）：

| 陷阱 | 实例 | 处置 |
|---|---|---|
| 展示用样例代码字符串 | 页面 `@State message0: string = \`…v.validate(instance, schema)\`` 只是**显示文本**，真机不执行 | 只在"代码位置"识别调用（扫描器把字符串内容清空后再匹配） |
| 成员访问 ≠ 导出函数 | `new Validator().validate(...)`、`this.validate()` 是接收者/自身方法；页面自己也有 `validate()` 方法 | 只认从本库 import 的绑定名；排除 `.name`/`?.name` 与 `name() {` 定义形态 |
| 单元测试 ≠ 真机 demo 覆盖 | 该库 `src/ohosTest` 下有 19 个 Hypium 测试文件在调这些接口 | 调用点分 `call`（src/main，真机可达）与 `test_call`（src/ohosTest），**分开统计，不得混同** |

实测结果（json-schema 2.0.2）：导出符号 16 个（class 1 / function 2 / const 5 / type 8）；
其中 **demo 真机调用 4 个**、仅单元测试调用 5 个、完全没有被调用 7 个。
这组数字就是 P3 覆盖矩阵的分子与分母。

**幂等与版本键**：`api_symbols` 的唯一键含 `library_version`，重新采集时按
`(library_id, library_version)` **先删后插** —— 只 upsert 的话，改了入口或删了导出后
旧符号会永远留在表里，分母永久失真。版本键取**库清单里声明的 version**（该库是 `2.0.2`），
不用 DB 缓存的 `current_version`：单体仓里 `git describe --tags` 会把别的样本的 tag 贴上来
（实测 json-schema 曾被标成 `ohos_minizip_1.0.5`）。

**顺带发现的 oracle 富矿**：该库 `src/ohosTest/tests/draft{4,6,7,2019-09,2020-12}/`
下带着上游 **JSON-Schema-Test-Suite** 的官方一致性用例。P6 的 oracle 与其靠 LLM 编，
不如优先绑定这类现成规范用例。

### 6.3 S3/P3 · 覆盖矩阵

**目标**：一张表回答"每个对外接口，在 demo 里有没有被用到？在真机上有没有对应控件？有没有负向用例？"

**装配来源**：

| 矩阵列 | 来源 |
|---|---|
| 接口 | `api_symbols` |
| demo 覆盖 | **静态**：在 demo 源码中检索符号名（`grep` 级 + AST 级）→ 记录调用点文件行号；**动态**：遍历时该页面 hilog 中出现的接口相关日志 |
| 控件 | 遍历报告：`page_path` + `control_ref`（node id） |
| 场景适用性 | §6.4 的规则层判定 |
| 风险 | `check compat` + 文档中"限制/注意"条目 + 无负向用例 |

**状态判定规则**（确定性，可单测）：

```
not_covered  : demo 源码中查不到该符号，且遍历中没有间接证据
partial      : demo 中有调用，但只有正向路径（无异常/边界用例）
covered      : 正向 + 至少一条负向
blocked      : 该接口无法通过 UI 触发（如需 API-only 调用）→ 进人工队列
```

**产出**：矩阵视图（前端表格，可按"未覆盖/风险"筛选）+ 导出能力（Markdown/CSV，便于评审）。

#### 6.3.1 P3 实现后按真实数据修正的结论

规则表落地时有三处设计稿没写清、但直接决定"结论可不可信"的地方，实现按下面处理：

1. **`covered` 的门槛不能降**。设计稿说 `partial = demo 中有调用但没有负向用例`，
   实现严格照此：**只有"demo 正向调用 + 至少一条负向(empty/boundary)用例"才判 covered**。
   demo 里有调用这件事本身只是"正向"，把它当覆盖就是假覆盖。
   `bigdata` 不算负向（它是压力场景，不是异常路径）。

2. **只有单元测试调用 → partial，不是 covered**。实测该库 16 个符号里有 5 个只被
   `src/ohosTest` 的 Hypium 测试调用。单元测试跑通 ≠ 真机覆盖，因此判 partial 并标
   `test_only` 风险，理由写明"真机路径未覆盖"。同理，"只被单测调用"也不能进 not_covered
   —— 那会掩盖"其实有人测过"这个事实。

3. **类型/接口符号一律 blocked**。类型没有运行时行为，真机 UI 既触发不了也断言不了。
   实测 16 个符号里 8 个是类型（TS 声明只存在于源码，编译产物被 gitignore）。
   这直接影响**接口覆盖率的分母**：分母取"可测符号"（排除 blocked），否则
   一个类型多的库覆盖率会天然难看，指标就失去指导意义。矩阵页会把这句写在指标下面。

**风险标记只标能拿出依据的**。`api_only`（只能 API 调用）**不由规则自动产生**：
静态分析只能证明"没找到调用"，证明不了"UI 触发不到"，硬标就是猜，留给人工/P5 写入。
同理 `name_only_signature` 只在**没定位到定义体**时才标 —— 一开始用"参数个数为 0"
代替，结果 16 个符号里误标 14 个（类有 16 个方法但构造无参也被标红），噪音把真问题全淹了。
为此 `api_symbols` 增加 `detail_level` 列（full / decl-only / name-only）并持久化。

**真机控件这一列的来源**：P1 的遍历报告里页面记录用的是点击路径（人看得懂），
而路由名只出现在操作轨迹的 `点击「X」→ 进入新页面 · pagePath=pages/Y` 里，
两者按控件标签拼起来，才能把源码里的 `pages/SimpleValidatePage` 对上真机页面。
拿不到就标 `no_device_control`，**绝不编造**。

实测结果（json-schema 2.0.2 首次构建）：16 行 = covered 0 / partial 8 / not_covered 0 / blocked 8，
接口覆盖率 0%（该库还没有任何用例）。风险分布：no_case 16、type_symbol 8、
name_only_signature 7、test_only 5、no_device_control 3。
这组数字正是 P4 要消化的输入。

### 6.4 S4/P4 · 初版用例集（四类场景）

**场景维度与适用性判定**（不是每个接口都有四类）：

| 场景 | 定义 | 适用条件（确定性规则） | 示例 |
|---|---|---|---|
| `happy` 正向 | 合法输入下的正常路径 | **全部接口必适用** | 播放动画 → 断言播放中 |
| `empty` 空值 | `null` / `undefined` / 空串 / 空数组 / 未初始化 | 参数可空，或类型为「可空/容器/字符串/对象」，或有 setter 类接口 | `setData('')`、未调用 `init` 直接 `play()` |
| `boundary` 边界异常 | 越界值、类型错误、超时、重复调用、逆序调用、权限拒绝、异常回调、资源释放后调用 | 参数有取值范围/上限，或接口有状态机/回调/异步 | `setProgress(999)`、连续 `play()` 两次、`release()` 后再 `play()` |
| `bigdata` 大数据 | 大文件/长列表/大数组/高分辨率/长时间运行 | 输入含尺寸/数量/时长参数，或接口处理集合/媒体/渲染 | 100MB JSON、1000 项列表、4K 图、连续播放 30 分钟 |

**数量模型**：

```
用例数 ≈ Σ_over_symbols ( 1                                     // happy，必做
                        + fit_empty   ? (1 + negExtra_empty)    // 空值
                        + fit_bound   ? (1 + negExtra_bound)    // 边界异常
                        + fit_bigdata ? 1 )                     // 大数据
          × (1 + 触发器数 - 1)                                  // 同一接口多个触发入口时按入口展开（可选）
```
其中 `negExtra_*` 由接口语义决定（如异常码有 3 种 → 边界类 +3）。

**工作量示例**（以 `lottie_turbo` 这类库量级估算）：导出符号 30 个，平均适用 2.4 个场景 → **约 72~110 条**，比当前"每页 1~2 条、40 页约 60 条"提升明显，且每条都有明确来源与目的。

**防爆炸策略**（重要）：
- 适用性矩阵先剪枝，**不为不适用的接口造用例**；
- 每条用例带 `priority`（P0 正向必跑 / P1 关键负向 / P2 长尾），执行计划可按优先级抽样；
- **抽样必须显式**：报告里写明"共 N 条，本次执行 M 条，未执行原因：优先级/预算"，绝不静默截断（这是修复记录里同类问题的教训）。

#### 6.4.1 P4 实现后按真实数据修正的结论

1. **"该造哪几条"必须与 LLM 无关**。适用性判定、负向条数、优先级全部由纯函数
   `casePlan.ts` 决定（可离线逐条核对），LLM 只负责把每条计划**写成具体用例**。
   把"该不该有这条"交给模型自由发挥，数量报告就失去了核对意义。

2. **`negExtra` 只用能拿出依据的口径**：`boundary` = 声明异常条数 + （有状态机生命周期方法 ? 1 : 0），
   `empty` = 可选参数 ≥2 时 +1。理由是"异常码有 3 种就多 3 条"这类判断必须能从签名/JSDoc 追到，
   不能靠感觉。实测 json-schema：`Validator` 有 11 个真方法（含 addSchema/getSchema/validateSchema），
   因此拿到 1 正向 + 1 空值 + 2 边界 + 1 大数据。

3. **触发器展开只扩 happy，且有硬上限**（默认 3）。`Validator` 在 demo 里有 17 个页面调用它，
   全展开会让单个符号吃掉整个预算。**截断必须在理由里写明**：
   "该接口在 demo 里共 9 个入口，本次按前 3 个展开以控制条数"。

4. **数量报告必须从实际计划里数出来，不能另算一遍**。第一版分解表是拿 `applicability`
   重新推的，而计划的触发器数已被上限截过，于是报告写着「正向 17 条」实际只生成 3 条 ——
   报告与计划不一致比没有报告更糟，因为它让人以为 17 个入口都覆盖了。
   现在 `summarizePlans` 是纯函数且单独自检（场景/优先级分布之和 = 总数、分解表各行之和 = 总数）。

5. **类的可测单元是它的方法，字段不是**。`Validator.prototype.customFormats = {}` 是**属性**，
   一开始被当成方法收进清单，于是输入设计变成"调用 customFormats()"这种不存在的东西。
   现在只收 `X.prototype.foo = function` / `= async (` 这类函数赋值。

6. **不可测符号不生成用例**。矩阵判定 `blocked` 的（类型/接口、废弃接口）直接跳过并在报告里列出，
   实测 8/16 个符号被跳过 —— 这是对的：给类型造真机用例纯属浪费。

实测结果（json-schema 2.0.2）：可测符号 8 个 → 计划 **20 条**
（正向 10 / 空值 3 / 边界 4 / 大数据 3；P0 10 · P1 7 · P2 3），跳过 8 个类型符号。
生成后会自动重算覆盖矩阵，在任务轨迹里给出「接口覆盖率 X% → Y%」的前后对比。

### 6.5 S5/P5 · demo 可测性判定与改造方案 ★

这是本设计中最"接地气"的一环：**每条用例必须先回答"现在能不能跑、不能跑要怎么改"**。

#### 判定分类

| 类 | 名称 | 判定条件（确定性） | 处置 |
|---|---|---|---|
| **A** | 开箱可测 | demo 已有入口控件，且参数由 UI 输入或走默认值即可满足用例输入 | 直接生成脚本 |
| **B** | 改参数可测 | demo 代码中存在该参数的字面量/常量（`demo_assets.kind='param'`），无需改结构 | 产出**参数替换补丁**（最小 diff） |
| **C** | 需改代码 | demo 未调用该接口，或没有对应控件/参数入口 | 产出**代码补丁草案**（新增调用/新增控件），并标注影响面 |
| **D** | 无法测 | 需要外部依赖（数据库/网站/其他设备）、媒体人工判定、物理操作、超长时运行 | 进人工接管队列 |

判定输入：`api_symbols`（签名/参数/异常）+ `demo_assets`（调用点、参数点、控件）+ 遍历控件清单 + 用例的输入设计。

#### 落地机制（关键约束）

1. **补丁只在独立副本上应用**：`workspace/demo-patches/<lib>/<caseNo>/`（从原 demo 复制或 `git worktree`），**绝不直接改用户仓库**。
2. **应用前静态校验**：⚠️ `check arkts` 不存在、`check lint` 在本机检查 0 个文件却 exit 0（§0.1），故**当前不做自动静态校验**——补丁草案标记"未经静态校验"，交由第 4 步人工评审。接任何静态检查前必须先过"正面对照"（注入坏文件必须被报出）。
3. **应用后必须能回退**：每个补丁携带 `revert` 指令与原始文件哈希。
4. **补丁要人工可评审**：补丁草案进前端"补丁评审"视图，人工点"批准"才应用到副本。
5. **人工批准过的补丁 → 知识沉淀**（§7 的 `demo_patch` 类条目），同类库下次可直接复用模式。

#### 6.5.1 P5 实现后按真实数据修正的结论

1. **判定必须对"所有"用例成立**，包括没有关联接口符号的历史用例 —— 设计验收项是
   "100% 用例带 A/B/C/D"。关联了符号的按 符号+场景 判；没关联的按
   **「用例步骤里引用的控件在真机上是否真的存在」** 判（步骤是同一套真机句式：
   点击「X」/输入「X」到「Y」/验证「X」，控件文本可直接与遍历报告比对）。
   两条路都拿不到依据的，也给 C 并写明"需要人工确认入口"，绝不留空。

2. **控件比对的范围是"整次遍历收集到的全部控件"**，不是"该符号所在页面的控件"。
   用例步骤通常是"先点首页入口、再点目标页按钮"，而首页在路由表里没有路由名
   （它不是"被进入"的页面）。只看目标页会把首页入口项判成"控件不存在"，
   于是**可执行的用例被塞进"需改代码"** —— 实测踩过：`Simple Object Validation`
   明明被遍历点过（它就是首页列表项），却被判成不存在。修完后 json-schema 的
   代表性用例从 A0/B0/C5/D1 变成 A1/B2/C2/D1（四类齐全）。

3. **B 类补丁必须支持多行模板字面量**。该 demo 的数据点几乎全是
   `@State xxx: string = 多行样例代码`（反引号包裹），只认单行等于放弃这一整类数据点
   （第一次跑出"补丁 0 处"就是这个原因）。现在按"反引号到反引号"整体取出字面量再替换。

4. **替换用「唯一子串」而不是按行号**：出现 0 次说明源码已变、多次说明位置不唯一，
   两种都拒绝应用。manifest 记录原始内容，回退按"找到 after 换回 before"精确还原。
   实测：`AllValidatePage.ets:21` 的多行字面量被成功替换，副本应用 1 处、失败 0 处，
   **原仓库文件全程字节未变**，回退后副本字节还原。

5. **找不到安全锚点时不生成补丁**，把位置与原因写进 `reason`（跨行/不唯一/读不到文件/
   没锚点）。硬凑一个改不对的补丁比不生成更坏。

实测（json-schema 2.0.2，6 条代表性用例）：A 1 / B 2 / C 2 / D 1，带补丁草案 3 条
（B 类 2 条可自动应用；C 类 1 条给出"新增控件"草案；另有 1 条 C 因找不到插入锚点转人工）。
补丁落地在 `workspace/demo-patches/<库>/<用例>/`，原仓库只读。

### 6.6 S6/P6 · 用例优化与 oracle

在现有 `optimizeCaseById` 基础上扩展，三个新增能力：

1. **补缺**：输入不仅是用例，还有"矩阵中该库的未覆盖项"，允许 Agent **新增**用例（而不是只改写）。
2. **oracle 强制**：每条用例必须产出机器可校验判据，取值域：
   | oracle 类型 | 判据 | 校验方式 |
   |---|---|---|
   | `control_text` | 界面出现/消失指定控件文本 | `ui layout` 检索 |
   | `text_value` | 指定控件文本等于/包含某值 | `ui layout` 读 text |
   | `hilog_keyword` | hilog 出现关键字（含错误码） | `devecocli log` |
   | `state_flag` | 控件 `checkable` 状态为真/假 | `ui layout` 读标志 |
   | `no_crash` | 执行期间无 E 级日志/无崩溃 | `devecocli log --level E` |
   | `screenshot_diff` | 截图像素差异在阈值内/外 | 截图对比 |
   | `script_assert` | 脚本内断言 | Hypium 断言 |
   **没有 oracle 的用例不允许进入"可自动化"分支**（只能进 A/B 人工判定或补 oracle）。
3. **反假通过**：结合 `dryRun` 与 oracle 校验，识别"脚本通过但断言为空"的情况（修 R12）。

#### 6.6.1 P6 实现后的结论（两条硬门槛怎么才不是数字游戏）

"断言覆盖率 100%、假通过 0"最容易变成刷数字：把"预期结果：功能正常"当成一条断言，
覆盖率立刻 100%，但真跑起来什么都判定不了。所以实现的重点是**拦住伪判据**：

1. **含糊的期望值一律拒绝**。`text_value` 的 value 若为「正常/成功/失败/功能正常/符合预期/
   可用/正确」等**判断性词语**，直接判为伪判据并拒绝入库，理由写明"必须写成界面上真正会出现的文本"。
   取舍是**刻意偏严**：这些词偶尔真的会显示在界面上（那时作者补上下文即可），
   而放行的代价是留下一条永远不可能失败的断言 —— 假通过的代价远大于改写一个词。
   反过来，机器字面量（`true`/`false`/`ok`/`0`）**必须放行**：该 demo 的界面就显示
   `实际结果：true`，不能因为"看着像布尔"就把合法断言拒掉（第一版误拒过，被自检抓住）。

2. **恒真断言与缺字段同样拒绝**：`assert true`、缺 `control`、缺 `value`、缺 `state`、
   阈值越界、空数组、`undefined` —— 全部不允许入库。数组里只要有一条伪判据，整条用例就不达标。

3. **反假通过的主线是"通过必须有依据"**：
   - 通过了但一条 oracle 都没有 → 假通过（最严重）；
   - 通过了但执行期间没有任何 oracle 被校验（`oraclesChecked=0`）→ 假通过；
   - 通过了但步骤里没有显式验证动作 → **弱通过**（提示补一步验证，不算假通过）；
   - **未通过的用例不属于假通过**（失败本身是有效信号）。

4. **"验证步骤"必须按句式开头判断，不能在整句里找"验证"两个字**：真机 demo 的按钮
   就叫「验证」（json-schema 每个页面都有一个），于是 `点击「验证」` 会被误认为验证步骤，
   任何点了这个按钮的用例都会"看起来有断言"。这条正是被自检抓出来的。

5. **生成端硬拦**：P4 的生成 Agent 现在必须为每条用例产出 `oracles`；校验不通过的
   **不写库**，并把原因写进任务轨迹（"因 oracle 不达标未入库 —— …"）。
   P6 之前生成的用例（`oracle_json='[]'`）不会被当成达标，质量看板会如实显示覆盖率 0% 并列出是哪几条。

6. **补缺**：优化 Agent（`optimizeCaseById`）现在会拿到"本库覆盖矩阵里仍未覆盖的接口"清单，
   可以在 `additions` 里新增用例；新增项**同样过 oracle 硬门槛**（补缺不是放宽标准的理由），
   不达标的逐条报出被拒原因。

实测（json-schema 2.0.2）：6 条 P5 期用例的断言覆盖率为 0%、硬门槛不达标 —— 这是**正确**结果
（它们确实没有可核验断言）。把其中一条标记为「通过」后，质量看板立刻抓出 1 条假通过
（"脚本通过但断言不可核验"）；给它补上一条合法 oracle 后假通过归 0、覆盖率升到 16.7%。
这两个方向都验过，闸门是真的会拦。

### 6.7 S7/P7 · 自动化可行性分流 + 人工接管队列

**确定性分流规则**（先规则、后 LLM，规则结果优先）：

```
可自动化 (auto) 当且仅当：
  testability ∈ {A, B, C 且补丁已批准}
  且 oracle 全部可机器校验
  且 不涉及：外部数据库/网络第三方/另一台设备/物理操作/媒体人工判定
  且 预计单次执行时长 < 阈值（默认 5 分钟）

否则 → 人工接管队列，并给出明确的阻塞类别与问题
```

**阻塞类别**：`demo_patch`（补丁待批准）、`animation`、`video`、`external_dep`、`oracle_missing`、`flaky`、`device_blocked`。

**人工接管队列界面**：每条含「原因 / 需要你做什么 / 上下文证据（截图、日志片段、补丁草案）/ 回填结论」四段。回填后：
- `demo_patch` 批准 → 应用补丁到副本 → 重跑该用例的可行性判定；
- `oracle_missing` 提供判据 → 重生成脚本；
- 结论一律沉淀为知识条目。

#### 6.7.1 P7 实现后的结论

1. **分流必须是规则，且规则结果优先于 LLM**。分流决定"这条用例到底会不会被自动执行"，
   交给模型自由发挥就无法核对。实现里 `classifyAutomation` 是纯函数，逐条可自检；
   阻塞类别也由规则给出（不是笼统的"需要人工确认"）。

2. **一次分流要列出全部阻塞，不能只报第一条**。一条用例常常同时缺 oracle、缺补丁、还没设备，
   只报一条会让人以为改完它就通了。实测一条用例最多命中 5 类阻塞。

3. **但队列条目按 stage 分别落库，每条只问自己的事**。第一版每条条目的「需要人做什么」
   写的是**全部**阻塞的动作合集，于是人打开"补丁待批准"这条，却被告知"顺便把 oracle 也补了" ——
   既重复又容易漏。现在每个 stage 只问它自己（自检里有专门一条：补丁条目不得出现 oracle 字样）。

4. **`screenshot_diff` 可以替代动画/视频的人工判定**。设计把 animation/video 列为阻塞类别，
   但若有像素差异判据，这两个就不该进人工队列 —— 规则里显式做了这个替代。

5. **补上 `long_running` 与 `untestable` 两个类别**。设计提到"预计单次执行时长 < 阈值（默认 5 分钟）"
   却未单列类别，而超时确实需要人决策（调阈值还是拆用例）；D 类用例也必须有明确归属。
   预计时长按"每步固定开销 4s + 显式等待时长"估算，未写等待的步骤按 1.5s。

6. **队列幂等且不误重置**：同一 (用例, stage) 只保留一条 open；已 resolved 的条目**不会**因为
   重复分流被重新打开，只有当阻塞原因变化时才重开（否则人刚填完结论又被重置）。

7. **回填 → 重跑分流是闭环**：结论里若带了合法的 oracle JSON，会**直接写入该用例**再重跑分流。
   实测：给缺 oracle 的用例回填一条 `text_value` 判据后，可自动化从 0 条变成 1 条；
   其他阻塞未解除的条目自动重新入队。

实测（json-schema 2.0.2，6 条用例）：可自动化 0 · 人工 6，阻塞分布 oracle_missing 6 ·
demo_patch 4 · untestable 1 · external_dep 1，队列 12 条（按 stage 分开）。
"可自动化 0"是**正确**结果：这些用例既没有可校验断言、也没有已批准的补丁。

### 6.8 S8/P8 · Hypium 脚本生成与映射联动

**保留**现有 `stepToPython` 句式契约（已有 19 项离线自检），新增：

1. **oracle → 断言**：`hilog_keyword` → 在脚本中读取 hilog 并断言；`state_flag` → `assert_component_exist` + 属性断言；`no_crash` → 执行后检查 E 级日志。
2. **未映射即失败**：`stepToPython` 无法映射的步骤，**不再生成注释行**，而是让脚本生成失败并回报（当前行为会产出"看起来正常"的脚本）。
3. **空脚本拦截**：生成后校验脚本至少含 1 个断言，否则拒绝绑定（修 R12）。
4. **映射与版本联动**（核心需求）：
   ```
   绑定时记录 case_versions.version → case_script_bindings.case_version
   用例每次升版：若 bindings.case_version < cases.current_version
                 → bindings.status = 'stale'
                 → 前端在用例卡与脚本卡同时提示「对应手工用例已更新到 Vx，脚本基于 Vy，请判断是否重新生成」
                 → 提供三个动作：重新生成 / 保留并标记已确认 / 解除绑定
   若 script_hash 与库中脚本内容不一致 → status = 'manual'（人为改过，不自动覆盖）
   ```
5. **执行结果回写**：脚本执行结果（通过/失败/耗时/日志）回写 `bindings`，用于 flaky 识别。

#### 6.8.1 P8 实现后的结论

1. **"未映射即失败"要落在生成函数里，不能靠人检查**。`stepToPython` 现在无法识别时返回 `null`，
   `generateCaseScript` 抛 `UnmappedStepError`（带步骤序号与原文），`writeCaseScript` 不落盘。
   旧行为是产出一行 `# 未映射步骤…` 注释 —— 脚本语法合法、"看起来正常"、跑完还"通过"，
   这正是 R12 的假通过形态。

2. **空脚本拦截用一条明确的判据**：脚本里必须出现 `assert` 语句、`assert_*()` 调用或
   `.assertXxx()` 方法调用，否则抛 `NoAssertionError` 拒绝绑定。实测：只有
   「打开应用 / 点击「验证」」的用例被拦下（而按钮恰好叫「验证」的坑在 P6 已单独处理）。

3. **oracle → 断言：`script_assert` 内联，其余六种统一走支持模块 `autotest_oracle.py`**。
   这样**只有一个地方需要按 Hypium 版本适配**，而不是把版本差异散落在每个脚本里。
   关键约束：支持模块里未实现的判据**一律 `raise AssertionError`**，绝不静默通过 ——
   判据没实现就"通过"，等于把没测的东西报成测过了。
   （`control_text` 的 appear 分支已用与既有脚本一致的 `assert_component_exist` 实现；
   text_value / state_flag / hilog_keyword / no_crash / screenshot_diff 的取值方式需要按
   实际 Hypium 版本补齐 —— 这些 API 我无法离线核实，所以做成"明确失败"而不是猜。）

4. **状态判定按优先级：`broken` > `manual` > `stale` > `fresh`**。把 `manual` 排在 `stale`
   之前是刻意的：人为改过的脚本已经不是生成产物，这时提示"可能过期"会误导人直接点重新生成、
   把手改内容覆盖掉。重新生成对 `manual` 默认**拒绝**，需要显式 `force`。

5. **状态是算出来的，不是落库的快照**：每次读取都按当前文件内容哈希 + 用例版本重新判定
   （`status` 列只是给列表查询用的缓存）。否则文件被删/被改之后，列表里还显示"最新"。

6. **哈希前统一换行符**：`\r\n` 与 `\n` 不算"人为改过"，否则 Windows 上每次 checkout 都误报。

实测（json-schema 2.0.2）：带 oracle 的用例绑定成功（脚本含 `from autotest_oracle import (`
与 `assert_text_value(...)`）；只有点击没断言的用例**拒绝绑定**；含无法映射步骤的用例
**拒绝绑定并指出第 2 步**。版本联动：用例升版 → `stale/可能过期`（提示"用例已更新到 V2，
脚本基于 V1"）；人工确认 → `fresh`；人工改脚本 → `manual/人工改过`，不确认就重新生成**被拦住**。

详见 §7。要点：人工确认的结论 → 结构化 Markdown 条目 → 无向量检索 → 注入后续任务的提示词。

## 7. LLM wiki 详细设计（无 GPU 约束）

### 7.1 为什么不做 RAG/向量库

| 维度 | 向量 RAG | LLM wiki（本设计选定） |
|---|---|---|
| 硬件 | 嵌入模型或外部嵌入 API；本地跑则要算力/内存（无显卡机器上体验差） | **零额外硬件**：纯文件 + 字符串匹配，与 Node 同进程 |
| 依赖 | 向量库（或 pgvector 等扩展） | 无；Markdown + JSON 索引 |
| 可解释性 | 相似度黑盒，"为什么召回这条"说不清 | 命中即命中：作用域键 + 关键词，可逐字解释 |
| 可审核 | 切片后语义割裂，人难审 | 一条 = 一个完整结论，人能直接读、直接改 |
| 可版本化 | 需额外同步机制 | **git 原生**：diff / blame / 回滚 |
| 当前语料规模 | 初期几百条，向量优势不体现 | 几百条 md 全量注入提示词都放得下 |
| 升级路径 | — | 语料变大或需要模糊召回时，**同一批 md 直接切片入向量库即可**，知识本身不用重写 |

**结论**：先用 wiki；把"检索"做成一等函数，将来换实现只替换该函数。**不锁死**。

### 7.2 存储格式

```markdown
---
id: kn-20260912-0007
scope_kind: library          # library | api | control | scenario | global
scope_key: lottie_turbo
kind: traversal_quirk        # traversal_quirk | oracle_recipe | special_handling
                             # | blocked_reason | demo_patch | human_verdict
title: 「无限循环」开关打开后遍历会卡在动画页
keywords: lottie 循环 loop 遍历 卡住 动画 超时
status: human_confirmed      # ai_draft | human_confirmed | rejected | deprecated
confidence: 90
evidence:
  - task: 128
  - explore: explore_1757...json
  - log: 片段见下
created_at: 2026-09-12T14:20:00Z
updated_at: 2026-09-12T15:02:00Z
---

## 现象
打开 demo 的「无限循环」开关后，页面持续重绘，`ui layout` 的节点坐标每次都在变，
基于坐标的候选去重永远命中不了，遍历在该页停留到超时预算耗尽。

## 原因
该页是持续动画页，坐标不稳定；按坐标分桶做页面签名会把每一帧都判为新页面。

## 处置（已验证）
1. 遍历前先关闭「无限循环」开关，最后再单独覆盖该开关的用例；
2. 该页的页面签名改用「控件 ID 集合」而不是坐标。

## 结论
- 人工确认：2026-09-12，确认有效（截图 + 遍历报告见证据）
- 适用范围：所有含持续动画的库，不限于 lottie_turbo
```

### 7.3 目录结构

```
workspace/knowledge/wiki/
├── index.json                      # 全部条目的元数据索引（自动生成，供检索）
├── libraries/<library>/<kind>/<slug>.md
├── apis/<library>/<symbol>.md      # 接口级结论（契约、坑、验证方式）
├── controls/<fingerprint>.md       # 控件级（某类控件的交互配方）
├── scenarios/<scenario>.md         # 场景级（大数据/超时/外设的通用处置）
└── global/<slug>.md
```
`index.json` 由扫描 md 的 front-matter 生成，**md 是唯一事实来源**（避免双写不一致）。

### 7.4 检索算法（三级，无向量）

```
输入：{ library, apiName?, controlFingerprint?, scenarioKind?, stage, budgetTokens }
1) 结构化命中（精确）：scope_kind+scope_key 精确匹配 且 status ∈ {human_confirmed, ai_draft}
      优先级：api > control > library > scenario > global
2) 关键词命中（倒排）：对剩余条目，用 apiName/控件文本/场景名 分词，命中 keywords 字段者按命中数排序
3) 排序与截断：
       score = 3*scope精确 + 2*关键词命中数 + (status==human_confirmed ? 2 : 0) + confidence/100
       按 score 降序取到 budget 为止，保证至少注入 1 条 library 级 + 1 条 scenario 级（若有）
4) 注入格式：标题 + 现象 + 处置 + 结论（不含 front-matter），并标注来源与置信度
```

**可单测**：检索函数是纯函数（输入条目数组 + 查询，输出选定条目），用 `scripts/verify-*.mjs` 的传统做契约自检。

### 7.5 注入策略与预算

| 阶段 | 注入内容 | 预算 |
|---|---|---|
| 遍历 | traversal_quirk（该库 + 全局） | 800 字 |
| 生成 | oracle_recipe + demo_patch（该库 + 涉及的接口） | 1500 字 |
| 优化 | 上述 + human_verdict | 1500 字 |
| 分流 | blocked_reason + special_handling | 800 字 |
| 脚本生成 | oracle_recipe + 句式契约已有的教训 | 1200 字 |

超出预算时按 score 截断，并在任务轨迹里记录**注入了哪些条目**（可追溯）。

### 7.6 生命周期与治理

```
AI 产出结论 → ai_draft（可注入，但低权重、UI 标注"未经人工确认"）
     ↓ 人工在知识页确认
human_confirmed（高权重，可跨库复用）
     ↓ 人工判定过时/错误rejected / deprecated（不再注入，保留供追溯）
```

- 每条条目必须带 `evidence`（任务/报告/截图/日志），否则不允许 `human_confirmed`；
- 库版本变化时，`scope_kind=api` 的条目若对应符号签名已变 → 自动降级为 `deprecated` 并提示复核；
- 条目正文可被人工直接编辑（md 文件），或用前端编辑器。

### 7.7 升级到 RAG 的预留

- 检索函数签名固定：`retrieve(query, entries, budget) -> Entry[]`；
- 将来加向量只需在函数内部加一路召回并融合排序，**调用方不改**；
- md 已经是天然切片单元，`content_hash` 已就绪。

#### 7.8 P9 实现后的结论

1. **md 是唯一事实来源，DB 只是索引**。`knowledge_entries` 由扫描 `workspace/knowledge/wiki/**/*.md`
   重建；条目正文与 front-matter 全在 md 里，人能直接读、直接改、git 可 diff。双写一定会不一致，
   而知识条目正是最不能悄悄错的东西。

2. **解析失败不抛错**：知识目录里可能有半成品或手写笔记，一条坏文件不该让整个知识库读不出来。
   `parseEntry` 返回 null，接口把它列进 `broken` 供人处理；非法枚举值（scope/kind/status）
   回落到安全默认，不产生非法状态。

3. **检索完全可解释**：命中理由逐条给出（"作用域精确命中(library:json-schema) · 人工已确认"），
   这是选 wiki 而不是向量库的直接好处。评分按 §7.4：`3*作用域精确 + 2*关键词命中 + 人工确认 2 + confidence/100`。
   实测：同库同作用域下，人工已确认的 5.85 分排在 AI 草稿 3.5 分之前。

4. **必注入规则与显式截断**：预算极小也保证至少注入 1 条库级 + 1 条场景级（若有）；
   被截断的条数会报出来（"因预算截断 N 条"），不静默丢弃。

5. **没有证据的条目不允许人工确认**（§7.6）。实测：`evidence: []` 的条目点确认直接被拒，
   理由写明"知识库不能收传闻"；有 1 条真实证据（任务/报告/日志引用）才允许。

6. **注入必须可追溯**：生成与优化阶段的提示词里注入经验后，**注入清单写进任务轨迹**
   （每条带命中理由 + 截断条数）—— 否则"为什么这次生成得好/不好"无从追溯。
   各阶段预算按 §7.5：遍历 800 / 生成 1500 / 优化 1500 / 分流 800 / 脚本 1200 字。

7. **人工队列的结论自动沉淀**（§6.7「结论一律沉淀为知识条目」）：回填结论时按
   stage → kind 映射生成 `ai_draft` 条目（demo_patch→补丁类、oracle_missing→判据配方、
   flaky→遍历怪癖…），并把条目 id 回报给前端。沉淀是草稿，需人工确认后才高权重参与注入。

## 8. Agent 绑定与替换

### 8.1 阶段即接口（stage contract）

每个阶段的输入输出**结构化约定**，与"用哪个 agent 实现"解耦：

| stage | 输入 | 输出（Schema 约束） |
|---|---|---|
| `api_extract` | 仓库路径 / HAR 产物路径 | `ApiSymbol[]` |
| `demo_parse` | demo 工程路径 | `DemoAsset[]` |
| `matrix_build` | symbols + assets + explore 报告 + compat 报告 | `MatrixRow[]` |
| `case_draft` | 矩阵切片（接口 + 场景 + 页面 + 控件） | `DraftCase[]`（含 scenario_kind、oracle、priority） |
| `case_optimize` | 现有用例 + 未覆盖项 + oracle 规则 | `DraftCase[]`（改写 + 新增） |
| `testability` | 用例 + demo 资产 | `TestabilityVerdict`（A/B/C/D + 理由） |
| `demo_patch` | C 类判定 + demo 源码 + 接口签名 | `PatchDraft[]` |
| `triage` | 用例 + 判定规则 | `Auto|Manual` + 阻塞类别 |
| `script_gen` | 用例 + oracle + 句式契约 | Hypium 脚本 + 映射记录 |

**约束**：每个 stage 的输出必须过 Schema 校验（类似现有 `llmJson` 的三保险），校验失败不允许进入下游。

### 8.2 内置 Agent vs 用户自写 Agent

- **内置 Agent**：随插件发布的 `prompts` 记录（seed 写入），role 与 stage 一一对应。
- **用户自写 Agent**：
  - 方式一：在「Prompt 管理」页新建/编辑模板（已有能力），绑定到某个 stage；
  - 方式二：在 `skills/` 下放一份 `SKILL.md`，绑定到 stage（`skill_path`）；
  - 方式三：**外部 Agent**——通过 MCP 调 `deveco-code`（§3.2）或任何 MCP 兼容 agent。

### 8.3 绑定与切换

- `agent_bindings` 表：stage → prompt/skill/model/params，支持 `global` 与按库覆盖；
- 前端「Agent 绑定」页：每个 stage 一行，可选择内置 / 自写 / 外部，显示当前生效配置与最近运行指标（成功率、平均耗时、token）；
- **可回滚**：切换即生效（下一任务），历史任务记录当时使用的绑定（可追溯"这条用例是哪个 agent 生成的"）。

### 8.4 与外部 Agent 互操作

- AutoTest 可**作为 MCP server** 暴露自己的工具（矩阵查询、用例读写、知识检索）给 `deveco-code` 等外部 agent；
- 也可**作为 MCP client** 消费 `devecocli serve mcp`；
- 两条都走 MCP，避免为每个外部工具写适配。

#### 8.5 P10 实现后的结论

1. **阶段清单固化在代码里**（`STAGES`，9 个阶段），每个阶段带输入输出约定、内置 prompt role、
   知识注入种类与预算。外部 agent 按同一份约定接入 —— 这是"不为每个工具写适配"的前提。

2. **绑定优先级：按库 > 全局 > 内置默认**。实测：默认 `builtin`（内置默认（用例生成））→
   设全局 prompt 后变为 `prompt · 全局绑定` → 设按库 skill 后该库变为 `skill · 按库绑定（库 #2）`，
   而其他库仍是全局的 prompt。所以"默认全用内置、个别库换自写 agent"是最省事的用法。

3. **非法绑定一律拒绝**：未知阶段、按库绑定没给 libraryId、绑 Skill 没给 skillPath、
   绑 Prompt 没给 promptId、绑外部 Agent 没给 externalCmd —— 全部 400 且说明缺什么。
   否则会出现"绑了但没生效"的静默失败。

4. **可追溯**：每次运行把生效绑定写进任务轨迹（`绑定TraceLine`：阶段 · 来源 · 实现方式 ·
   prompt/skill/model/params）。这直接回答"这条用例是哪个 agent 生成的"。

5. **MCP 服务端只实现核心三个方法**（`initialize` / `tools/list` / `tools/call`，JSON-RPC 2.0
   over HTTP）。刻意不实现 stdio 传输、resources/prompts、会话协商 —— 够用，且每一处行为都可核对。
   暴露 7 个工具：接口清单、覆盖矩阵、用例读、用例写、知识检索、人工队列、质量门槛。
   **`case_write` 强制要求 `oracles`**：外部 agent 写入路径同样守住 P6 硬门槛
   （断言为空的用例是假通过，不能因为是外部写的就放行）。

## 9. 覆盖率与质量度量

| 指标 | 定义 | 目标（首版） | 展示位置 |
|---|---|---|---|
| 接口覆盖率 | 有用例的导出符号 / 全部导出符号 | ≥ 90% | 首页 KPI + 矩阵页 |
| 场景维度覆盖率 | Σ(已覆盖维度) / Σ(适用维度) | ≥ 80% | 矩阵页 |
| 控件覆盖率 | 收录控件 / 发现控件 | ≥ 95%（且未收录原因可见） | 遍历报告 |
| 可执行率 | (A+B+C已批准) / 全部用例 | ≥ 85% | 用例页 |
| 自动化率 | 已生成脚本（且非 stale） / 可自动化用例 | ≥ 80% | 脚本页 |
| 断言覆盖率 | 带可机器校验 oracle 的用例 / 全部用例 | **100%**（硬门槛） | 用例页 |
| 假通过率 | 脚本通过但断言为空/无断言的用例数 | **0**（硬门槛） | 质量看板 |
| 知识复用率 | 生成时注入了知识条目的任务 / 全部任务 | 观察项（不设阈值） | 知识页 |

**硬门槛**（不达标直接阻断）：断言覆盖率 100%、假通过 0。这两条正是当前最严重的两个质量漏洞（R9、R12）。

## 10. 风险与边界

### 10.1 明确做不到的

- **"接口有 bug" 的自动判定**：没有 oracle 就没有"对错"。系统只能给出"异常信号 + 证据"（hilog E 级日志、崩溃、断言失败、返回值异常展示），判定权给人。
- **动画/视频内容的自动判定**：需要帧差/专用工具或人工。本设计将其归入人工队列，不做假承诺。
- **UI 状态全覆盖**：见 §2.2。

### 10.2 设备与性能约束（无显卡机器）

- **真机优先**：`deveco-cli` 的 `ui/device/run` 走真机不需要显卡；本设计的主路径不依赖模拟器。
- **模拟器为可选增强**：其硬件加速/显卡要求未在 README 中明确，**列为待验证项**；若目标机器跑不动，退化为真机 + 物理操作。
- **LLM 调用**：走 DSH 已配置的模型（云端），本地无模型推理需求 —— 与"无显卡"不冲突。
- **大数据场景的资源风险**：长时间运行/大文件可能引发设备发热、OOM、掉设备。必须有单用例时长上限、执行前电量检查（`emulator battery` 或真机电量）、失败熔断。

### 10.3 demo 改造的污染风险

**硬规则**：
1. 永远不直接修改用户的 demo 仓库；
2. 所有补丁在**独立副本**（`workspace/demo-patches/<lib>/<caseNo>/`）上应用；
3. 补丁必须携带 `revert` 与原始文件哈希；
4. ~~补丁必须先过 `check arkts` 再构建~~ → **`check arkts` 不存在（§0.1）**：改为"补丁草案 + 人工评审"，构建校验视工程 hvigor 可用性而定（本机 json-schema 的 hvigor 3.0.2 与现工具链不兼容，构建亦不成立）；
5. 人工批准是补丁生效的前置条件（AI 只能出草案）。

### 10.4 对 deveco 工具链的依赖风险

- 版本地板：Node ≥ 22、DevEco Studio ≥ 6.0/6.1、Command Line Tools ≥ 26；
- 平台限制：deveco-code 不支持 Linux；macOS 下 Studio 需装在特定目录；
- 命令输出格式可能随版本变化 → **所有解析走 `--format json`**，并在启动体检里记录版本号（输出格式不合预期时降级并告警）。

## 11. 分期计划与验收

| 期 | 内容 | 交付物 | 验收标准 | 估算 |
|---|---|---|---|---|
| **P1** | 遍历可信化：候选/去重/分类交互/预算制/覆盖率报告 | 重写的 `uiExplorer` + deveco 工具层 + 覆盖率报告页 | 埋点验证：无文本图标按钮、下拉框、Tab 页、三级子页面全部被采集；报告可解释每条跳过 | 3~5 天 |
| **P2** | 接口面提取 + demo 资产解析 | `api_symbols` / `demo_assets` + 接口清单文档 | 导出符号 100% 入库（与人工抽查一致）；demo 调用点可定位到文件行 | 2~3 天 |

| **P4** | 矩阵驱动用例生成（四类场景） | 生成 Agent + 适用性规则 + 数量模型 | 每接口 ≥1 正向；适用维度全覆盖；数量报告可解释 | 3~4 天 |
| **P5** | 可测性判定 + 补丁草案 + 补丁评审视图 | 可测性规则 + `demo_patch` + 评审/应用/回退 | 100% 用例带 A/B/C/D 判定；C 类补丁可应用、可回退、构建通过 | 4~5 天 |
| **P6** | oracle 强制 + 优化补缺 + 反假通过 | oracle Schema + 优化 Agent 改造 + 硬门槛校验 | 断言覆盖率 100%；假通过 0 | 3~4 天 |
| **P7** | 分流 + 人工接管队列 | 分流规则 + 队列界面 + 回填闭环 | 每条用例有明确归属；回填后能触发下游重跑 | 2~3 天 |
| **P8** | Hypium 生成增强 + 映射联动 | 断言映射 + `case_script_bindings` + 过期提示 | 手工用例升版 → 脚本卡出现"可能过期"提示并可一键重生成 | 3~4 天 |
| **P9** | LLM wiki 知识库 | 条目格式 + 检索函数 + 知识页 + 注入 | 人工确认的结论在下次同类任务中被引用（轨迹可见） | 3~4 天 |
| **P10** | Agent 绑定与切换 + 外部 agent 互操作 | `agent_bindings` + 绑定页 + MCP 出入口 | 任一 stage 可切到自写 agent 并生效；历史任务可追溯到绑定 | 3~4 天 |

**建议顺序**：P1 → P2 → P3 是不可跳的前置（分母、事实、矩阵）；P4 起才谈生成质量。若时间紧，可先做 P1+P2+P3 交付一次评审。

**每期的共同要求**（沿用本项目已确立的纪律）：
- 规则层纯函数 + 离线自检脚本（无设备、无 LLM、无 DB）；
- 新增表走 MySQL/SQLite 双 schema + 编号迁移；
- 接入 CI 门禁，不达标不发布。
