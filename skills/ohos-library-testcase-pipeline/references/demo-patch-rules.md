# demo 最小改造规范（S5）

C 类用例（现有 demo 没有入口或没有参数注入点）要改代码才能测。这一节管的是**改得安全、可验证、可回退**。

## 四条铁律

1. **只在工程副本上改**：`<工作区>/demo-patches/<库名>/<用例号>/`（复制原工程或 `git worktree`）。
   **绝不直接修改用户的仓库** —— 改坏了不是"测试失败"，是破坏别人的东西。
2. **最小侵入**：优先"新增"而不是"修改"。新增一个按钮/一个参数注入点，不动既有逻辑。
   改一行常量可以，重写一个页面不行。
3. **可回退**：每个补丁带 `before` / `after` / 文件 / 大致行号 / 说明，且能一键还原。
   **改完不能还原的补丁不许生成。**
4. **改完必须验证**：`devecocli build --modules <模块>` 通过 → `devecocli run --module <模块>` 装到真机 →
   该场景**真的能触发**（截图/日志/dump 为证）。**改完不验证 = 没做**。

## ⚠️ 工具链自己会改写工程（实测，动手前必须留基线）

在**用户仓库**上直接跑 `devecocli build` / `run`，实测会发生：

| 文件 | 改动 |
|---|---|
| `build-profile.json5` | `compileSdkVersion/compatibleSdkVersion: 10` → `"26.0.0"`；`runtimeOS: "OpenHarmony"` → `"HarmonyOS"`；自动补 `signingConfigs` |
| `oh-package.json5` | `modelVersion: ""` → `"26.0.0"` |
| `hvigorw` / `hvigorw.bat` / `hvigor/hvigor-wrapper.js` | **被删除**（换成工具链自带的 hvigor） |
| `library/BuildProfile.ets` | 构建生成的新文件（未跟踪） |

也就是说"我只是构建一下"并不成立：**工程的目标平台与 SDK 版本被就地改了，被测对象也跟着变了**。

所以：

1. 动手前先 `git status --porcelain` 记基线；
2. 能只在**副本**上构建就只在副本上构建；真机验证必须用原仓库时，构建后立刻核对 diff；
3. 工具链改动要**写进报告**（别让它变成"没人知道的改动"），并给出一行还原命令：
   `git checkout -- <被改的文件>` + 删除构建生成的未跟踪文件；
4. 如果用户本来就希望把老工程升级到新 SDK，那是**另一件事**，要单独确认，不能夹在测试流程里悄悄做。

## 改造方式：从最轻到最重

| 级别 | 做什么 | 风险 | 是否需要人确认 |
|---|---|---|---|
| 1 | 改 demo 里的**测试数据常量**（把 `'abc'` 改成 `''`，把长度 10 改成 10000） | 极低 | 否 |
| 2 | **新增**一个注入不同数据的按钮/开关（保留原入口不动） | 低 | 否 |
| 3 | **新增**一个测试页面并在主页加一个入口 | 中 | 建议告知 |
| 4 | 改 **library 里的库代码**（改签名/加参数/改行为） | 高 | **必须人确认** |

到第 4 级就说明被测对象变了：这时候要先问"是真的需要改库，还是 demo 造不出入参？
还是这个场景本来就该归 D 类（无法测）？"

## ArkTS 会拦住你的写法（实测）

补丁写完**必须先构建**，因为 ArkTS 的强约束会让"看起来正常"的 JavaScript 写法直接编译失败：

| 写法 | 结果 | 正确写法 |
|---|---|---|
| `let instance = {};`（无类型对象字面量） | ❌ `arkts-no-untyped-obj-literals` 编译失败 | `let instance: Record<string, ESObject> = {};` 或先定义 interface |
| 动态属性访问 `obj[key]` | 常被拒 | 用 `Record<...>` 或显式类型 |
| 任意类型 `any` | 被拒 | `ESObject`（本项目 demo 的惯用法） |

**空值与边界场景几乎都要传"结构不对"的入参，正好最容易踩这条** —— 所以补丁的第一版构建失败是常态，
不是意外；构建失败 → 看编译器给出的错误码与规则名 → 改成显式类型 → 再构建。

## 补丁结构

```json
{
  "caseNo": "C-AI-007",
  "need": "大数据场景：需要 1 万个条目才能验证分页",
  "file": "entry/src/main/ets/pages/PagingPage.ets",
  "before": "private items: Item[] = buildItems(10)",
  "after":  "private items: Item[] = buildItems(10000)",
  "note": "仅改测试数据量，不改页面逻辑",
  "revert": "把 10000 改回 10（或整文件还原）",
  "verify": ["devecocli build --module entry", "devecocli run --module entry", "进入分页页 → 观察条目数与滚动是否正常"],
  "risk": "1 万条可能触发长列表性能问题；若卡顿，记录耗时而不是判失败"
}
```

## 应用补丁的匹配规则（这里是真会改错地方的地方）

- 用**唯一子串**匹配定位：`before` 在文件里必须**恰好出现 1 次**；
- 出现 **0 次**（内容与预期不符，可能源码已更新）或 **>1 次**（会改错地方）→ **拒绝应用**，
  不要"就近猜一个"；
- 应用前记录原文件哈希，回退时校验是否还原成功（**回退后应字节一致**）；
- 路径必须在工程目录内（拒绝 `..` 越界路径）。

这三条是硬要求：宁可拒绝，也不改错位置。

## 什么时候不该自动改，转人工

| 情况 | 处置 |
|---|---|
| 需要外部数据库/服务/第二台设备 | 转人工队列（D 类），写清"需要什么环境" |
| 需要真实网络、真实账号、支付流程 | 转人工队列 |
| 需要观察动画/视频/音画同步 | 转人工队列；若有截图判据可自动化的部分另说 |
| 需要跑几十分钟以上 | 转人工队列，或降级为"抽样跑一次 + 人工确认" |
| 改库代码才能测 | **停下来问人**，说明改动内容与影响 |

## 验证证据要留什么

每条 C 类用例至少留三样：**补丁本身**、**构建结果**、**真机触发证据**（截图或 hilog 片段 + 触发的控件路径）。
缺哪样就算哪样没做，并在报告里如实写"未验证"。
