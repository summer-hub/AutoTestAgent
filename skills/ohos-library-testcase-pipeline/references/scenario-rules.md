# 场景规则与可测性判定（S4）

## 四类场景

| 场景 | 造什么 | 算负向吗 | 典型形态 |
|---|---|---|---|
| `happy` 正向 | 常规合法输入，走通主路径 | 否 | 传入合法数据 → 期望正常结果 + 无异常 |
| `empty` 空值 | 空串 / 空数组 / 空对象 / `null` / `undefined` / 未设置 / 空文件 / 空数据源 | **是** | 传 `[]`、`''`、`null` → 期望明确报错或降级，而不是崩溃 |
| `boundary` 边界异常 | 极值、临界值、非法类型、越界索引、重复调用、**状态机乱序**（未 start 就 stop / start 两次） | **是** | 传 `-1`、超大值、错误类型 → 期望抛声明异常或返回可判定结果 |
| `bigdata` 大数据 | 超大集合、超长文本、大文件、高频刷新 | **否**（压力维度） | 1 万条记录 → 期望不崩溃、耗时在可接受范围 |

## 适用性：不适用就写明理由，**不硬造**

硬造不存在的场景是这份产出最容易出现的假覆盖。逐条按下列依据判定：

| 场景 | 什么时候**适用** | 什么时候**不适用**（要写进报告） |
|---|---|---|
| happy | 恒适用（除 `deprecated`/纯类型） | — |
| empty | 有可选参数；有容器/字符串/数组参数；有 `set*`/`reset`/`clear` 类接口；能构造空数据源 | 参数全是必填标量且无语义空值；接口本身就是"创建"语义且空值无意义 |
| boundary | 有声明的异常/错误码；有数值或范围参数；有长度/尺寸限制；是状态机方法（start/stop/reset/close）；有索引或分页 | 纯 getter 且无输入；无可变状态的对象 |
| bigdata | 有尺寸/容量/数量类参数；接受集合、媒体、渲染数据；有超时或性能相关契约 | 行为与数据量无关的纯逻辑接口 |

判定要点：

- **看签名与 JSDoc，不看感觉**：`@param {number} size` + 有上界说明 = boundary 适用；
  `@param {string} [encoding]` 带方括号 = 可选 = empty 适用。
- **状态机方法**：从接口名与文档里找 `start/stop/open/close/init/destroy/release` 一类的配对，
  配对存在就至少有一条"乱序/重复调用"的边界用例。
- **异步接口**：至少一条"失败/拒绝"路径（网络失败、超时），若无法稳定构造 → 归 D 类。

## 用例条数模型（数量要能解释）

```
某个接口的用例数 = 适用的场景维度数 + 额外负向条数
额外负向条数 = 声明的异常/错误码条数（封顶 2） + (是状态机方法 ? 1 : 0) + (可选参数 ≥ 2 ? 1 : 0)
```

报告里必须能对上：**"为什么不适用"与"为什么只有这几条"都要写出来**。
数量报告与实际情况不一致，比没有报告更糟（让人以为覆盖了 17 个入口，实际只测了 3 个）。

## 触发器展开（一个接口有多个 demo 入口时）

一个接口可能在 demo 里被多个页面/按钮调用。**默认每个接口只取前 N 个入口（建议 N=3）**，
因为全展开会吃掉整个预算。截断必须写明：`共 7 个入口，本次取前 3 个（页面 A/B/C）`。
**静默截断是不允许的** —— 读者会以为 7 个都覆盖了。

## 可测性 A/B/C/D（决定要不要改代码）

| 类 | 判定依据 | 处置 |
|---|---|---|
| **A 开箱可测** | 现有 demo 的页面 + 控件就能触发，且结果能在界面上观察到 | 直接写用例 |
| **B 改参数可测** | 需要换测试输入（空值/极值），但 demo 里那个输入点存在（常量、`@State`、输入框默认值） | 在**工程副本**上改测试数据；不改库代码 |
| **C 需改 demo 代码** | 没有入口，或没有参数注入点：大数据场景要生成大集合、异常场景要先绕过前置校验、目标接口压根没被 demo 调用 | 走 S5：产出最小改造 → 构建 → 真机验证 |
| **D 无法测** | 需要外接数据库/第二台设备/真实网络；需要人工判断（动画流畅度、音画同步）；需要数小时级耗时；需要特殊硬件 | 进**人工接管清单**，写清"需要人做什么" |

判定顺序：先问"界面上能不能触发"，再问"输入能不能改"，再问"改代码值不值"，最后才认 D。
**不要一上来就把难题推给 D 类**——那等于用"人工"掩盖"没做"。

### 常见误判

| 误判 | 纠正 |
|---|---|
| "demo 里搜到这个接口名 = A 类" | 先排除样例代码字符串与成员调用（见 coverage-matrix.md 的三种假覆盖） |
| "能让它崩就算测了异常" | 崩溃是缺陷证据，不是通过标准；用例要写"期望的异常/提示文本或错误码" |
| "大数据场景现成 demo 跑一下就行" | 先确认 demo 的数据量能调大；不能就是 C 类，需要传参与入口 |
| "D 类写'环境限制'就够了" | 必须写**具体需要人做什么**（如"在 XX 页面手动播放 3 分钟并观察是否卡顿"） |
