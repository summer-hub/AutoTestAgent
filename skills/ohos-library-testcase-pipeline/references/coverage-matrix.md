# 覆盖矩阵口径（S3）

矩阵是这一整套里**唯一能证伪"覆盖够不够"的东西**。它的价值不在结论，而在每一行都能被人拿去核对。

## 分母：什么算"要测的接口"

| 符号类型 | 进分母？ | 理由 |
|---|---|---|
| `function` / `class`（含其方法）| ✅ 进 | 有运行时行为，真机能触发、能断言 |
| `enum` / 常量 | ✅ 进（弱） | 多数无需真机用例，标 `trivial` 并在报告里说明 |
| `type` / `interface`（纯 TS 声明）| ❌ **不进** | 编译期产物，真机上既触发不了也断言不了。**排除在外**，不要用它们拉低覆盖率 |
| `deprecated` | ✅ 进但标风险 | 废弃接口不该再补用例，标出来让人决定 |

> 对外宣称覆盖率时，分母写"**可测符号**"，并在同一行注明"另有 N 个类型/接口声明不计入"。
> 不写这句，读者会以为覆盖率被挑了分母。

## 行里的列

| 列 | 来源 | 缺失时怎么写 |
|---|---|---|
| 接口名 / 类型 / 签名 | S1 接口清单 | — |
| 源码位置 | S1（`file:line`）| `未定位`（不要说"大概在 library/index.ts"） |
| demo 调用点 | `src/main` 源码扫描：本库导出的名字在该页被调用 | `无` |
| 单测调用点 | `src/ohosTest` 扫描（**单独一列**，不可与上一列合并） | `无` |
| 真机可达页面 | demo 调用页 ∩ 真机遍历出现过的页面 | `无遍历证据` |
| 真机控件 | 上一步命中页面的控件清单（来自 dump） | `未获取` |
| 已有用例 | 关联到该接口的用例号（正向/负向分列） | `无` |
| 状态 / 判定理由 | 见下 | — |
| 风险 | 见下 | — |

## 状态判定（按优先级从上往下判定，命中即停）

| 状态 | 判定条件 | 判定理由要写什么 |
|---|---|---|
| **不可测 blocked** | 类型/接口声明；或需要外部系统/人工观察/不可复现条件 | 写清"为什么测不了" |
| **未覆盖 not_covered** | demo 里没有真实调用，也没有单元测试调用，且没有用例 | 写清"缺什么" |
| **部分覆盖 partial** | ① 只有单元测试调用；② 或 demo 有调用但**只有正向用例**（缺空值/边界负向）；③ 或有用例但 demo 无调用 | 分别写"仅单测调用，真机未验证" / "只有正向，缺负向" / "用例未在 demo 上落地" |
| **已覆盖 covered** | demo 里**真实调用过** **且** 至少一条**负向用例**（空值或边界异常） | 写出调用点与负向用例号 |

三条硬规则：

1. **大数据场景不算负向**。大数据是压力维度，把它当负向就等于用"跑得动"冒充"异常处理正确"。
2. **单测 ≠ 真机覆盖**。只被 `src/ohosTest` 调用判 partial，且它也不能判 not_covered —— 那会掩盖"其实有人测过"。
3. **宁可判 partial 也不判 covered**。把"没测"报成"测了"是本流水线最严重的错误。

## 三种假覆盖（必须分开统计，不许合并）

| 形态 | 实例 | 为什么是假的 |
|---|---|---|
| 展示用**字符串**里的调用 | 页面写着 `@State sample: string = "v.validate(x)"` 只是给人看的样例代码 | 真机根本不执行 |
| **成员调用** ≠ 导出函数 | `new Validator().validate(...)`、`this.validate()`，页面自己也有同名方法 | 不能证明"导出的那个 validate 被测了" |
| **单元测试**调用 | `src/ohosTest` 下的 Hypium 测试调这些接口 | 单测跑通 ≠ 真机路径通 |

统计口径：`demoCall`（`src/main`）与 `testCall`（`src/ohosTest`）分列，**永不合并**。

## 风险标记（只标能拿出依据的）

| 标记 | 触发条件 |
|---|---|
| `no_case` | 一个用例都没有 |
| `no_negative_case` | 有调用/有用例，但全是正向 |
| `type_symbol` | 类型/接口声明 |
| `test_only` | 只被单元测试调用 |
| `no_traversal_evidence` | 没有真机遍历/dump 可对照 |
| `no_device_control` | 有遍历证据，但该接口的页面在真机上没对上 |
| `name_only_signature` | 没定位到定义体，只有名字（参数/异常都不可信，**别据此设计输入**） |
| `deprecated` | 已废弃 |
| `trivial` | 枚举/常量等无需真机用例 |

**明确不自动标的**：`api_only`（"UI 触发不到"静态证明不了，硬标就是猜）。这类结论只能由人给出，
或由 S5 改造尝试失败后得出。

## 真机控件是怎么对上页面的（最容易做错的一步）

同一页在两处写法不同，**必须显式对齐**：

- 接口的 demo 调用点记的是**路由名**（`pages/SimpleValidatePage`，来自源码）；
- 真机遍历/操作轨迹里记的是**点击路径面包屑**（`首页 → 简单校验`）。

对齐办法：从操作轨迹里抽 `点击「X」→ 进入新页面 · pagePath=pages/Y` 这样的记录，用"被点控件的标签"
把面包屑与路由名连起来；两者对上之后，才能取到该页的真机控件清单。

对不上时**不要猜**：列 `no_device_control`，并在报告里说明"该页可能是首页入口/弹窗，遍历没记到路由名"。

## 导出

- `.md`（给人看/评审）：接口、类型、状态、判定理由、风险、适用场景、证据
- `.csv`（给机器/表格）：表头与数据都要加引号，列顺序固定，便于 diff

导出后**抽查 3 行**：随便挑三条状态各异的接口，看证据能否顺着文件行号与用例号查回去。查不回去就是证据链断了。
