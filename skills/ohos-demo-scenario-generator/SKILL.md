# ohos 三方库 Demo 测试场景生成技能

本技能通过分析已 ohos 化三方库的接口规格文档，自动生成完整的 Demo 测试场景列表，覆盖正向与反向（异常）场景，输出文件命名为 `{库名}Demo场景.md`，放置在当前目录下。

> ⚠️ **核心约束**：所有场景内容必须基于接口规格文档中真实存在的接口和功能生成，严禁凭空捏造不存在的接口、参数或行为。

---

## 适用场景

- 为已 ohos 化三方库规划 Demo 验证方案
- 生成覆盖正向 + 反向的完整测试场景集
- 评估库在异常/边界条件下的稳定性
- 为 QA 和开发团队提供可执行的测试参考
- 配合 `library-interface-analyzer` 技能，实现"接口分析 → 场景生成"完整链路

---

## 输入要求

执行前确认以下信息：

| 输入 | 是否必需 | 说明 |
|------|---------|------|
| **接口规格文档路径** | 必需 | 已 ohos 化三方库的接口规格文档（通常为 `*规格.md`、`*API文档.md`、`*Readme.md`） |
| **库源码路径** | 可选 | 提供后可补充接口规格文档未覆盖的细节（如默认值、错误码） |
| **输出目录** | 可选 | 默认放置在接口规格文档所在目录 |

---

## 工作流程

### 阶段一：读取并解析接口规格文档

#### 1.1 读取文档内容

```
执行步骤：
1. read_file 读取接口规格文档全文
2. 提取库名称（用于输出文件命名）
3. 识别文档结构（按模块/类/函数组织方式）
```

提取以下核心信息：
- **库名称**：用于生成输出文件名 `{库名}Demo场景.md`
- **功能模块划分**：文档中的模块/章节列表
- **导出的类列表**：类名、职责说明
- **方法列表**：每个方法的名称、参数、返回值、功能描述
- **枚举/常量列表**：可选值及其含义
- **错误码/异常类型**：文档中明确列出的错误码、异常类、失败状态
- **约束条件**：文档中注明的使用限制（如最大长度、必填参数、线程限制等）

#### 1.2 整理接口能力清单

将提取的信息整理为结构化的能力清单：

```
能力清单结构（内部工作记录，不写入输出文件）：
┌─────────────────────────────────────────────────────────────┐
│ 模块 A                                                       │
│   - 核心功能点 1（对应接口：methodA, methodB）                │
│   - 核心功能点 2（对应接口：methodC）                         │
│ 模块 B                                                       │
│   - 核心功能点 3（对应接口：classX.init）                    │
│   ...                                                        │
│ 错误/异常类型：                                               │
│   - ErrorCode.INVALID_PARAM（参数非法）                      │
│   - ErrorCode.TIMEOUT（超时）                                 │
│   - ErrorCode.NOT_INITIALIZED（未初始化）                    │
│   ...                                                        │
└─────────────────────────────────────────────────────────────┘
```

若接口规格文档中未明确列出错误码，则根据接口性质推断常见反向场景（见[反向场景通用模型](references/SCENARIO_TEMPLATE.md)）。

---

### 阶段二：场景规划

#### 2.1 正向场景规划原则

正向场景应覆盖该库的**主要功能路径**，遵循以下原则：

1. **功能覆盖**：每个主要功能模块至少有 1 个正向场景
2. **完整流程**：优先设计端到端的使用流程（初始化 → 配置 → 执行 → 获取结果）
3. **典型用法**：基于接口规格文档中的示例代码或使用说明
4. **组合场景**：包含多个接口协同使用的综合场景

**正向场景数量参考**：
- 接口 ≤ 10 个：规划 3~5 个正向场景
- 接口 11~30 个：规划 5~8 个正向场景
- 接口 > 30 个：规划 8~12 个正向场景，按模块分组

#### 2.2 反向场景规划原则

反向场景应覆盖该库在**异常和错误条件下的行为**，目的是验证库的健壮性和错误处理能力。

**反向场景必须涵盖的类别**（从接口规格文档中选取适用的类别）：

| 类别 | 适用条件 | 场景举例 |
|------|---------|---------|
| 参数非法 | 所有有参数的接口 | 传入 null/undefined、超出范围的值、错误类型 |
| 未初始化调用 | 需要初始化的类/模块 | 跳过初始化直接调用功能接口 |
| 资源不存在 | 操作文件/网络/数据库等资源 | 访问不存在的文件、断开的网络连接 |
| 并发/重复操作 | 有状态管理的接口 | 重复初始化、同时发起多个请求 |
| 超时/中断 | 异步/网络/IO 操作 | 操作超时、中途取消 |
| 边界值 | 接受数值/字符串/数组的接口 | 空字符串、最大值、负数、空数组 |
| 资源耗尽 | 占用内存/文件句柄/连接池的接口 | 内存不足、连接数上限 |
| 权限缺失 | 需要系统权限的操作 | 未申请权限直接调用 |
| 回调/Promise 异常 | 异步接口 | Promise 拒绝、回调抛出异常 |

**反向场景数量参考**：
- 正向场景数量 × 0.6 为下限（向上取整）
- 每个正向场景对应至少 1 个反向场景

#### 2.3 场景列表规划（内部工作记录）

在生成输出前，整理场景编号和类型：

```
场景规划表（内部）：
序号 | 场景名称 | 类型（正向/反向） | 涉及接口 | 所属模块
-----|---------|-----------------|---------|--------
S01  | ...     | 正向             | ...     | ...
S02  | ...     | 正向             | ...     | ...
...
S0N  | ...     | 反向             | ...     | ...
```

---

### 阶段三：生成场景详情

对每个场景按照以下结构生成详情：

#### 场景结构模板（7 要素）

```markdown
### [序号] 场景名称

**场景类型**：正向 / 反向

**场景描述**
[2~4 句话描述该场景的使用背景、操作步骤和预期结果]

**现象描述（可观察表现）**
[从设计经理视角，以 APP 页面交互方式描述，无需技术术语：
- **页面布局**：Demo 页面包含哪些 UI 元素（图片展示区、按钮名称、输入框、状态标签等）
- **触发操作**：用户点击哪个按钮或执行何种交互来触发该场景
- **可见结果**：操作后页面上发生的视觉变化（图像效果变化、文字内容更新、颜色变化、弹窗提示等）
每项描述具体到 UI 元素名称和视觉状态，使设计经理无需了解代码即可理解和验收该场景。]

**场景涉及的功能点**
- 功能点 1（对应接口：`ClassName.methodName()`）
- 功能点 2（对应接口：`ClassName.methodName2()`）
- ...

**关键体验指标**
- 指标 1：[可量化或可验证的指标，如"接口调用响应时间 < 100ms"]
- 指标 2：[...]
- ...

**用户期望**
[描述用户在该场景下的期望行为，即"做 X 操作后，希望得到 Y 结果"]

**场景设计关注点**
- 关注点 1：[需要特别验证或注意的技术/体验细节]
- 关注点 2：[...]
- ...
```

> 完整场景模板和各字段填写指南见 [references/SCENARIO_TEMPLATE.md](references/SCENARIO_TEMPLATE.md)。
> 场景示例见 [references/EXAMPLES.md](references/EXAMPLES.md)。

### 阶段四：生成输出文档

#### 4.1 确定输出文件路径

```
输出文件路径规则：
1. 若用户指定了输出目录 → 输出到该目录
2. 否则 → 输出到接口规格文档所在目录
文件名：{库名}Demo场景.md（库名取接口规格文档中提取的库名）
```

#### 4.2 输出文档结构

按以下结构生成 Markdown 文档：

```markdown
# {库名} Demo 测试场景

## 概述

- **库名称**：{库名}
- **文档生成时间**：{当前日期}
- **基于文档**：{接口规格文档文件名}
- **场景总数**：{总数}（正向 {N} 个，反向 {M} 个）
- **功能覆盖模块**：{模块列表}

## 功能模块映射

| 模块 | 主要接口 | 正向场景 | 反向场景 |
|------|---------|---------|---------|
| ... | ... | S01, S02 | S0N |

## 场景列表

### 正向场景

[各正向场景详情，按场景结构模板填写]

---

### 反向场景

[各反向场景详情，按场景结构模板填写]
```

#### 4.3 创建输出文件

使用 `create_file` 工具创建 `{库名}Demo场景.md`，写入完整文档内容。

## 质量自查清单

生成输出文档前，逐项确认：

- [ ] **场景数量充足**：正向场景覆盖所有主要功能模块；反向场景 ≥ 正向场景数 × 0.6
- [ ] **内容真实**：所有场景涉及的接口名称、参数名、返回值均来自接口规格文档，无捏造
- [ ] **7 要素完整**：每个场景均包含名称、描述、现象描述、功能点、关键体验指标、用户期望、设计关注点
- [ ] **现象描述直观**：现象描述以 APP 页面布局、按钮交互和视觉效果表达，设计经理无需了解代码即可理解和验收每个场景
- [ ] **反向场景有价值**：反向场景覆盖参数非法、未初始化、边界值等有意义的异常类别；避免重复设计相似的反向场景
- [ ] **指标可量化**：关键体验指标尽量具体，避免模糊描述（如"快"→ 改为"< Xms"）
- [ ] **用户期望明确**：用户期望描述清晰，包括操作主体、操作动作和期望结果
- [ ] **设计关注点有针对性**：每个场景的设计关注点指向该场景的特殊性，而非通用套话
- [ ] **文件命名正确**：输出文件名为 `{库名}Demo场景.md`
- [ ] **文档结构完整**：包含概述、功能模块映射、正向场景、反向场景四大部分
