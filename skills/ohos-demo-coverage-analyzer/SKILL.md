# ohos 三方库 Demo 场景覆盖率分析技能

本技能通过对比 Demo 场景文档与现有工程 entry 目录中的 Demo 代码，自动生成 Demo 场景覆盖率分析报告，量化评估覆盖程度，识别覆盖盲区，输出文件命名为 `{库名}Demo场景覆盖率报告.md`，放置在当前目录下。

> ⚠️ **核心约束**：所有覆盖率判断必须基于 Demo 场景文档中的真实场景和 entry 目录中的真实代码，严禁凭空推断覆盖或未覆盖。

---

## 适用场景

- 评估已有 Demo 代码对规划场景的覆盖程度
- 发现 Demo 覆盖盲区，指导 Demo 代码补充优先级
- 作为 Demo 开发完成后的质量验收依据
- 配合 `ohos-demo-scenario-generator` 技能，实现"场景规划 → 代码实现 → 覆盖率分析"完整闭环
- 为 QA 和开发团队提供 Demo 补充的可执行建议

---

## 输入要求

执行前确认以下信息：

| 输入 | 是否必需 | 说明 |
|------|---------|------|
| **Demo 场景文档路径** | 必需 | 由 `ohos-demo-scenario-generator` 生成的 `{库名}Demo场景.md` |
| **工程 entry 目录路径** | 必需 | 鸿蒙工程中包含 Demo 代码的 entry 模块目录，通常为 `entry/src/main/ets/` |
| **输出目录** | 可选 | 默认放置在 Demo 场景文档所在目录 |

---

## 工作流程

### 阶段一：解析 Demo 场景文档

#### 1.1 读取场景文档全文

```
执行步骤：
1. read_file 读取 Demo 场景文档全文
2. 提取库名称（用于输出文件命名）
3. 识别文档结构（概述、功能模块映射、正向场景、反向场景）
```

提取以下核心信息：
- **库名称**：用于生成输出文件名 `{库名}Demo场景覆盖率报告.md`
- **场景总数**：正向场景数 + 反向场景数
- **每个场景的要素**：
  - 场景编号（S01、S02 ...）
  - 场景名称
  - 场景类型（正向/反向）
  - 场景描述
  - 涉及的功能点及对应接口
  - 关键体验指标
  - 用户期望
  - 设计关注点

#### 1.2 整理场景清单

将提取的场景信息整理为结构化的场景清单：

```
场景清单结构（内部工作记录，不写入输出文件）：
┌──────────────────────────────────────────────────────────────────┐
│ 场景 S01：基础 GET 请求获取数据                                      │
│   类型：正向                                                        │
│   涉及接口：axios.get(url, config?)                                  │
│   关键指标：响应时间 < 200ms、返回数据结构与规格一致                    │
│                                                                    │
│ 场景 S02：POST 请求提交 JSON 数据                                    │
│   类型：正向                                                        │
│   涉及接口：axios.post(url, data?, config?)                         │
│   关键指标：请求体正确序列化、响应数据完整返回                          │
│ ...                                                                │
│                                                                    │
│ 场景 S0N：传入无效 URL 发起 GET 请求                                 │
│   类型：反向                                                        │
│   涉及接口：axios.get(url, config?)                                  │
│   关键指标：抛出包含错误码和描述的错误、应用不崩溃                       │
└──────────────────────────────────────────────────────────────────┘
```

### 阶段二：扫描 entry 目录现有 Demo 代码

#### 2.1 识别 entry 目录结构

```
执行步骤：
1. glob 递归扫描 entry 目录下所有 .ets / .ts 文件
2. 识别 Demo 相关文件（通常在 entry/src/main/ets/pages/ 或 entry/src/main/ets/ 下）
3. 忽略非 Demo 文件（如 Ability 文件、纯配置文件、资源文件）
```

典型的鸿蒙工程 entry 目录结构：

```
entry/
├── src/
│   └── main/
│       ├── ets/
│       │   ├── entryability/       ← 忽略（Ability 文件）
│       │   ├── pages/              ← 重点扫描（Demo 页面）
│       │   │   ├── Index.ets       ← 主入口页面
│       │   │   ├── HttpDemo.ets    ← HTTP Demo 页面
│       │   │   └── ...
│       │   ├── model/              ← 辅助扫描（数据模型）
│       │   ├── common/             ← 辅助扫描（公共工具）
│       │   └── viewmodel/          ← 辅助扫描（视图模型）
│       ├── resources/              ← 忽略
│       └── module.json5            ← 辅助参考（路由配置）
```

#### 2.2 提取 Demo 代码中的功能实现

对每个 Demo 相关文件，提取以下信息：

```
执行步骤：
1. read_file 读取每个 Demo 文件全文
2. 提取文件中调用的库接口（import 语句、函数调用、类实例化）
3. 提取文件中实现的交互逻辑（按钮点击、输入处理、结果展示）
4. 识别文件对应的场景主题（从文件名、注释、页面标题推断）
```

需要提取的信息：
- **调用的库接口**：从 import 语句和函数调用中提取（如 `axios.get()`、`axios.create()`）
- **交互行为**：用户可触发的操作（如按钮点击事件中的逻辑）
- **异常处理逻辑**：是否有 try/catch、错误回调、Promise reject 处理
- **页面功能描述**：从注释、Text 组件内容、页面标题推断

#### 2.3 整理 Demo 代码能力清单

将提取的代码信息整理为结构化的能力清单：

```
Demo 代码能力清单（内部工作记录，不写入输出文件）：
┌──────────────────────────────────────────────────────────────────┐
│ 文件：Index.ets                                                    │
│   调用接口：axios.get(), axios.post()                              │
│   交互行为：点击"GET请求"按钮发送 GET、点击"POST请求"按钮发送 POST    │
│   异常处理：有 try/catch，展示错误信息                              │
│                                                                    │
│ 文件：InterceptorDemo.ets                                          │
│   调用接口：axios.interceptors.request.use(),                      │
│            axios.interceptors.response.use()                       │
│   交互行为：点击"添加拦截器"按钮、展示拦截结果                       │
│   异常处理：有拦截器错误回调                                        │
│ ...                                                                │
└──────────────────────────────────────────────────────────────────┘
```

### 阶段三：场景与代码匹配分析

#### 3.1 匹配规则

对每个场景按照以下规则判断覆盖状态：

| 覆盖状态 | 判定条件 | 说明 |
|---------|---------|------|
| **✅ 完全覆盖** | 场景涉及的所有接口均有代码调用，交互逻辑完整覆盖场景描述的核心操作，异常处理逻辑覆盖反向场景的预期行为 | Demo 代码可完整验证该场景 |
| **🔶 部分覆盖** | 场景涉及的部分接口有代码调用，但缺少某些接口的调用或某些交互步骤；或正向逻辑存在但异常处理不完整 | Demo 代码只能验证场景的部分功能 |
| **❌ 未覆盖** | 场景涉及的接口在 Demo 代码中均未出现，或交互逻辑与场景完全不相关 | 无 Demo 代码可验证该场景 |

#### 3.2 匹配维度

匹配分析从以下维度进行：

**维度一：接口覆盖**
- 场景中"涉及的功能点"列出的每个接口，是否在 Demo 代码中被调用
- 计算接口覆盖率 = 已调用接口数 / 场景涉及接口总数

**维度二：交互路径覆盖**
- 场景描述的操作步骤，是否在 Demo 代码中有对应的用户交互（按钮、输入、结果展示）
- 正向场景：初始化 → 配置 → 执行 → 获取结果的完整路径是否实现
- 反向场景：异常触发条件是否可模拟，错误处理是否可验证

**维度三：体验指标覆盖**
- 场景的关键体验指标，是否可通过 Demo 代码进行验证
- 指标类型：性能类（响应时间）、功能类（数据准确性）、稳定性类（不崩溃）

**维度四：设计关注点覆盖**
- 场景的设计关注点，是否在 Demo 代码中有针对性的验证逻辑

#### 3.3 匹配结果表（内部工作记录）

```
场景匹配结果表（内部）：
场景编号 | 场景名称 | 覆盖状态 | 接口覆盖率 | 交互路径覆盖 | 指标覆盖 | 关注点覆盖 | 匹配文件
--------|---------|---------|-----------|------------|---------|-----------|--------
S01     | ...     | ✅ 完全覆盖 | 3/3 (100%) | ✅ | ✅ | ✅ | Index.ets
S02     | ...     | 🔶 部分覆盖 | 1/2 (50%)  | 🔶 | ❌ | ❌ | Index.ets
S0N     | ...     | ❌ 未覆盖  | 0/2 (0%)   | ❌ | ❌ | ❌ | —
```

### 阶段四：生成覆盖率分析报告

#### 4.1 确定输出文件路径

```
输出文件路径规则：
1. 若用户指定了输出目录 → 输出到该目录
2. 否则 → 输出到 Demo 场景文档所在目录
文件名：{库名}Demo场景覆盖率报告.md（库名取 Demo 场景文档中提取的库名）
```

#### 4.2 输出文档结构

按以下结构生成 Markdown 文档：

```markdown

  - ✅ 完全覆盖：{X} 个（{X/总数}%）
  - 🔶 部分覆盖：{Y} 个（{Y/总数}%）

- **整体覆盖率**：{(X + Y×0.5) / 总数 × 100}%（完全覆盖计 1.0，部分覆盖计 0.5，未覆盖计 0）

#### S0N {场景名称}
- **未覆盖原因**：{为什么没有对应 Demo 代码}
```

## 质量自查清单

生成输出文档前，逐项确认：

- [ ] **场景解析完整**：Demo 场景文档中所有场景均已提取并参与匹配
- [ ] **代码扫描全面**：entry 目录下所有 Demo 相关文件均已扫描分析
- [ ] **接口匹配准确**：每个场景涉及接口的覆盖判断基于代码中真实的 import 和调用，无主观臆断
- [ ] **覆盖状态有据**：完全覆盖/部分覆盖/未覆盖的判定有明确的匹配证据支撑
- [ ] **差距说明具体**：部分覆盖场景的差距说明指向缺失的具体接口或交互逻辑
- [ ] **补充建议可执行**：每个未覆盖/部分覆盖场景的补充建议包含具体要添加的代码逻辑
- [ ] **优先级合理**：高优先级聚焦核心功能和正向场景，低优先级为增强性反向场景
- [ ] **模块统计准确**：功能模块覆盖率基于场景覆盖状态汇总，数值可验证
- [ ] **文件命名正确**：输出文件名为 `{库名}Demo场景覆盖率报告.md`
- [ ] **文档结构完整**：包含概述、场景覆盖详情、未覆盖场景详细分析、功能模块覆盖统计、Demo 代码文件清单、补充开发优先级建议六大部分
