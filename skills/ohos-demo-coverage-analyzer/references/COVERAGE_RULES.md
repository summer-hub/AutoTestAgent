# 覆盖率判定规则与示例

本文档定义 Demo 场景覆盖率分析的匹配维度、覆盖判定规则、优先级评估规则和边界情况处理。

---

## 一、匹配维度详细说明

### 1.1 接口覆盖

**定义**：场景中"涉及的功能点"列出的每个接口，是否在 Demo 代码中被调用。

**判定方法**：
1. 从 Demo 场景文档中提取每个场景"涉及的功能点"中列出的接口签名
2. 在 Demo 代码中搜索对应的 import 语句和函数/方法调用
3. 统计已调用接口数 / 场景涉及接口总数

**匹配规则**：

| 代码中的调用形式 | 是否匹配接口 | 示例 |
|----------------|------------|------|
| 直接函数调用 | ✅ 匹配 | `axios.get(url)` 匹配 `axios.get(url: string, config?)` |
| 方法调用 | ✅ 匹配 | `instance.post(url, data)` 匹配 `AxiosInstance.post()` |
| 属性访问 | ✅ 匹配 | `config.timeout` 匹配 `AxiosRequestConfig.timeout` |
| 静态方法调用 | ✅ 匹配 | `axios.create(config)` 匹配 `axios.create()` |
| 通过变量间接调用 | ✅ 匹配 | `const fn = axios.get; fn(url)` 匹配 `axios.get()` |
| 仅 import 未调用 | ❌ 不匹配 | `import axios from '...'` 但未使用 `axios.get()` |
| 注释中提及 | ❌ 不匹配 | `// TODO: 调用 axios.cancel()` |

### 1.2 交互路径覆盖

**定义**：场景描述中的操作步骤，是否在 Demo 代码中有对应的用户交互实现。

**判定方法**：
1. 从场景描述中提取操作步骤序列（如"初始化 → 配置 → 执行 → 获取结果"）
2. 在 Demo 代码中查找对应的交互元素（Button 组件的 onClick 回调、输入事件等）
3. 判断交互链路是否完整

**交互元素识别**：

| 代码元素 | 对应交互 |
|---------|---------|
| `Button('xxx').onClick(() => {...})` | 按钮点击触发操作 |
| `TextInput().onChange((val) => {...})` | 输入框值变化触发配置 |
| `Toggle().onChange((isOn) => {...})` | 开关切换触发配置 |
| `List().onItemClick(() => {...})` | 列表项点击触发操作 |

**正向场景交互路径覆盖**：
- 完整路径：初始化 → 配置 → 执行 → 结果展示，四个环节均有交互实现 → ✅
- 缺少环节：有执行但无配置入口，或有结果但无展示 → 🔶
- 完全缺失：无对应交互实现 → ❌

**反向场景交互路径覆盖**：
- 有异常触发机制（如传入非法参数的按钮、断网模拟开关等）且错误可展示 → ✅
- 有异常处理代码但用户无法主动触发 → 🔶
- 无异常相关交互 → ❌

### 1.3 体验指标覆盖

**定义**：场景的关键体验指标，是否可通过 Demo 代码进行验证。

**判定方法**：
1. 从场景中提取每个关键体验指标
2. 判断 Demo 代码中是否有验证该指标的逻辑或展示

**指标验证方式**：

| 指标类型 | 验证方式 | 代码特征 |
|---------|---------|---------|
| 响应时间 | 计时展示 | `startTime = Date.now()` + 结果展示耗时 |
| 数据准确性 | 结果展示 | `Text(JSON.stringify(response.data))` |
| 错误信息完整 | 错误展示 | `Text(error.message)` |
| 系统稳定性 | 异常后可继续操作 | catch 后 UI 状态可恢复 |
| 资源释放 | 无法直接验证 | 代码中有 destroy/close 调用 |

### 1.4 设计关注点覆盖

**定义**：场景的设计关注点，是否在 Demo 代码中有针对性的验证逻辑。

**判定方法**：
1. 从场景中提取每个设计关注点
2. 判断 Demo 代码中是否有针对该关注点的特殊处理或验证

## 二、覆盖状态判定规则

### 2.1 判定矩阵

| 接口覆盖率 | 交互路径 | 体验指标 | 设计关注点 | 综合判定 |
|-----------|---------|---------|-----------|---------|
| 100% | ✅ 完整 | ✅ 可验证 | ✅ 有验证 | ✅ 完全覆盖 |
| 100% | ✅ 完整 | 🔶 部分 | 🔶 部分 | 🔶 部分覆盖 |
| ≥ 50% | 🔶 部分 | 🔶 部分 | ❌ 无 | 🔶 部分覆盖 |
| < 50% | ❌ 缺失 | ❌ 无 | ❌ 无 | ❌ 未覆盖 |
| 0% | ❌ 缺失 | ❌ 无 | ❌ 无 | ❌ 未覆盖 |

### 2.2 特殊情况处理

**情况一：场景涉及的接口是配置属性（非方法调用）**

例如场景涉及 `AxiosRequestConfig.timeout`，Demo 代码中通过对象字面量设置：
```typescript
axios.get(url, { timeout: 5000 })
```
→ ✅ 算作接口覆盖（配置属性通过对象字面量使用也算调用）

**情况二：多个场景共用同一 Demo 页面**

例如 S01（基础 GET 请求）和 S08（无效 URL 发起 GET 请求）共用 Index.ets：
- S01 调用 `axios.get('https://valid-api.com/data')` → ✅
- S08 需要调用 `axios.get('invalid-url')` 且验证错误处理 → 判断是否有错误触发逻辑

**情况三：反向场景通过正常流程触发异常**

例如 S09（POST 请求携带过大请求体），Demo 代码中有 POST 按钮但无"发送过大请求体"的入口：
- 接口覆盖：`axios.post()` 被调用 → ✅ 接口覆盖
- 交互路径：无法主动触发"过大请求体" → 🔶 交互路径部分覆盖
- 综合判定：🔶 部分覆盖

**情况四：场景文档中的接口名与代码中实际使用的接口名不完全一致**

例如场景文档写 `axios.get()`，代码中写 `http.get()`（通过别名 import）：
- 需要追踪 import 链：`import axios as http from '...'` → `http.get()` 等同于 `axios.get()`
- → ✅ 算作接口覆盖

## 三、优先级评估规则

### 3.1 优先级分级

| 优先级 | 适用条件 | 说明 |
|-------|---------|------|
| 🔴 高 | 正向场景未覆盖，涉及核心功能接口 | 核心功能缺失，用户无法验证基本使用 |
| 🔴 高 | 多个场景共同依赖的基础接口未覆盖 | 基础能力缺失，影响多个场景 |
| 🟡 中 | 正向场景部分覆盖，缺少非核心接口 | 核心可用但不完整 |
| 🟡 中 | 反向场景未覆盖，涉及常见异常 | 用户无法验证错误处理 |
| 🟢 低 | 反向场景未覆盖，涉及罕见异常 | 锦上添花，非必要 |
| 🟢 低 | 设计关注点未覆盖 | 深度验证，非基本需求 |

### 3.2 优先级排序规则

1. 正向场景优先于反向场景
2. 核心功能模块（请求发送、基础调用）优先于辅助功能模块（拦截器、取消请求）
3. 多场景共用的缺失接口优先于单场景缺失接口
4. 低工作量补充优先于高工作量补充（在同等重要性时）

## 四、整体覆盖率计算

### 4.1 计算公式

```
整体覆盖率 = (完全覆盖数 × 1.0 + 部分覆盖数 × 0.5 + 未覆盖数 × 0) / 场景总数 × 100%
```

### 4.2 模块覆盖率

```
模块覆盖率 = (模块内完全覆盖数 × 1.0 + 模块内部分覆盖数 × 0.5) / 模块内场景总数 × 100%
```

### 4.3 接口覆盖率

```
场景接口覆盖率 = 场景已调用接口数 / 场景涉及接口总数 × 100%
全局接口覆盖率 = 所有场景已调用接口总数 / 所有场景涉及接口总数 × 100%
```

> 注意：同一接口被多个场景引用时，在全局接口覆盖率中分别计算（不做去重）。
